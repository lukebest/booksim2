无缓存环上的 per-core 写带宽公平性

本次只跑 1 个 plane / 1 条 ring、均匀 tiled 写、 S0 与 S1。REQ / RSP / DAT 上下环口独立。 每 core 20000 笔 WriteNoSnp （请求量 ×10），每笔 2 个 WriteData flit。 HA 回 RSP / Comp 时延 0（无 HA think time） 拍。

结论

  1. 三通道链路独立。makespan 下界改由最忙 DAT/RSP hop 决定（bound 70000，port 50000 已松）。 Hop 理想全环 WriteData R* = 40/7 ≈ 5.714。
  2. tracker 加到 256 后彻底不再绑定。 S0 吞吐 4.5408 flit/cycle， 重试 0.0 次/事务， 峰值占用 195 个表项（没顶到 256）， 延迟 p50 = 43998。 与无限 tracker 参照逐拍一致（makespan 88090 vs 88090，吞吐同为 4.5408）。
    三轮对照：32 → 2.3848，128 → 3.04， 256 → 4.5408。 定尺寸的正确依据是 ∞ 参照在官方 K 上的峰值占用 195，而不是短跑扫描曲线的拐点 —— K=4000 的探测说 128 就够，官方 K 上并不够（见 3.1.3）。
  3. 每 VC 上环源队列 8+1 → 12+8： S0 4.5408 → 4.5408 flit/cycle （+0.00%）。 没有跨过 3% 证伪线；更深队列只保存更多待发 flit，没有解决 transit flit 抢占出链路造成的空槽时序。
  4. S1 相对 S0 吞吐 -0.2%，max/min 1.0104 → 1.0139。 本轮已无 RetryAck 可减，源端限速对 hop 理想毫无帮助。
  5. S0 达不到 R* 仍只剩一个已识别的原因：无缓存环的上环仲裁。 S0 吞吐是 hop 理想 R* 的 79%。 其余候选的状态：端口速率已排除（每节点每 VC 上/下环各 1 flit/cycle 折算成 8.0 flit/cycle，比 R* 还松，见 3.1.1）； 源/方向 buffer 深度（本轮 8+1 → 12+8 实测 +0.00%）、 completer 表项已排除（本轮 retry = 0）。 剩下的机制是在环 flit 绝对优先，核只能挤进空隙 —— 决定上环延迟的是空档的分布而不是总量。见 3.1 与 4.5。
  6. 上环失败比大 ≠ 访存不均衡。失败比是同一核 CW/CCW 失败次数比， 不是失败率。8 个 HA 收包相等；本轮核间写带宽也齐。 它是邻 mem = 1 的核在热 hop 上打不进去的症状。见 4.3.2。
  7. 官方 K 上没有一组 S1 参数让所有核失败比都 < 2。 最接近是 dir_split + harsh（2.07，仍有 C0/C8）。 各核写带宽仍是一条平线，只比默认 S1 低约 4%。见 5.2。

2. 指标：分箱 Jain（主）、max/min 与吞吐

  • 分箱 Jain（公平性主指标，进验收线）：把争用窗口切成 50 拍宽的箱，每箱内对 10 个 core 那一箱的 写带宽算一次 Jain，再对所有箱取平均。它回答「任一时刻各核是否均衡」。
  • 零模型与判定：50 拍内每核只有十来个 flit，纯计数噪声就让 Jain 到不了 1.0，而且这个地板随吞吐移动，所以绝对阈值没有意义。 把每箱总数 N 等概率撒到 n 个核上有 E[J] ≈ N/(N+n−1)，逐箱平均即 jain_bin_null；判定用比值 ratio = 实测/零模型 ≥ 1.0，含义是至少和完全公平的仲裁一样齐。 本轮 S0 = 0.98183 / 零模型 0.96197 = ratio 1.02064。
  • max/min（整窗）：降为诊断项，不进验收线。它仍然有用， 因为分箱 Jain 是二次指标、看不见个别核被饿死，而 max/min 直接读最坏的核。 均匀写下各方案的分箱 Jain 差异小于噪声（S0 0.98183 vs S1 0.98173）， 这是均匀写本来就公平的正确反映；流量不均时它分得很开。
  • 吞吐：公平性可以靠把所有人一起压慢买到，所以必须一起报。

验收线：分箱 Jain ≥ 同窗零模型且吞吐相对基线不下降超过 1%。

3.1 全环总写带宽的理论值，以及实测随时间的曲线

三条 VC 各有自己的上 / 下环端口，所以端口不再是最紧的资源， 反而是最忙那条 dat 链路绑定：14 对 (core, mem) 的 WriteData 要压在同一段 hop 上，每对每笔写 2 个 flit。

每节点每 VC 上环 1 flit/cycle、下环 1 flit/cycle （上环是两个方向共用那一个口，不是每方向 1；下环是 PE 每拍从该 VC 读 1 flit）。 把这条速率约束单独算成一个上限，要对四类口分别数：

最紧的是 8 个 mem 的 dat 下环口：每个每拍只能交给 PE 1 个 WriteData flit，所以全环 WriteData ≤ 8.0 flit/cycle。 这正是 LB_port 报的 8.0 flit/cycle （400000 flit ÷ 50000 拍）。
但 8.0 > 5.714，所以这条约束不绑定 —— 理论上限仍由最忙那条 dat 链路给出，R* = 5.714 不变。 换句话说，端口速率还有 40% 的余量， 瓶颈在链路而不是端口。

为什么链路比端口紧：端口是「每个节点自己的 1 flit/cycle」， 10 个核分摊得开；而 14 对 (core, mem) 的 WriteData 必须挤过同一段 hop，那一段每拍也只有 1 flit/cycle。节点数多不解决单段拥塞。 下一节的实测占用率印证了这一点：端口最忙的也只到 57%。

4.3.2 上环失败比大代表什么

「失败比」是同一个核两条出边的失败次数比 max(CW, CCW) / min，不是失败率。 黄底仍是比 ≥ 2 且该侧合计 ≥ 50。

S0 各核失败率其实都差不多（41%–44%）。 大的是方向比：成功比最大 1.00，失败比最大 2.59。 S0 失败偏的核 C0、C8、C10、C18， S1 为 C0、C8、C10、C18。

不会造成 8 个 mem 收写不均。 地址 interleave 已均衡，本轮 HA 收到的 WriteData 全部相同（50000 / HA）。 本轮也没有造成核间整窗写带宽不均 （S0 max/min = 1.0104）。 闭环批量下每核配额相同，落后的核能在收尾段补回来。 但它确实对应位置效应：带宽与邻 mem 数 r = 0.8129（本轮环就是唯一的瓶颈， 基线与 ∞ 参照同一条轨迹，max/min = 1.0104）。 失败比大的核就是邻 mem = 1 的那些核。 失败比大 = 这一侧出 hop 常被在环 flit 占着，本地尝试打不进去； 它是位置效应的症状，不是 mem 收包不均的原因。 本研究是纯写；读的 CompData 走反向同一组热 hop，机制相同。

为什么失败比会很大

  1. 最短路确定。N9 / N19 不接 HA，C10 的近端在 CW（M11）， C18 在 CCW（M17）。成功次数已经按这个需求偏到约 1.00。
  2. 偏的那一侧正好是全环最热的 hop（0→1、8→7、10→11、18→17）， 各被 14/80 条 (core, HA) 流穿过。
  3. 在环 DAT / RSP 有绝对优先，本地注入只能等空槽。 热侧是「尝试更多 × 成功率更低」，成功比仍约 1.00， 失败比被放大到 ≥ 2。两侧都是 mem 的核（如 C4 / C14）失败比 ≈ 1。

S1 改的是节点总预算，不改最短路，也不改在环优先， 所以失败比还在，只是换了一批核。

4.4 有限 tracker（256 个表项）：本轮不影响归因

吞吐相对无限 tracker +0.0%， max/min 1.0104 vs 1.0104， 重试 0.0 次/事务。 ∞ 参照峰值占用 195 表项 < ha_track = 256，配额从未触发， 所以基线与参照是同一条轨迹 —— 上面那套（环受限）的归因直接就是基线的归因，不需要再折算。
前两轮不是这样：32 表项时重试 0.602 次/事务、 吞吐 2.3848，128 表项时 0.1078 / 3.04，retry churn 会把几何因素部分盖住。

4.5 理想拥塞控制下的注入率（三 VC 链路独立）

REQ / RSP / DAT 的有向 hop 各有一份 σ=1 信用，互不占槽。 一笔事务仍要三条腿都走完，所以事务率受三张平面里最紧的那张限制： λ ≤ min(λ_REQ, λ_RSP, λ_DAT)。 本小节不把三 VC 叠进同一个上下环口。 λ* 是完成事务率，不是含重试的 REQ 上环次数。

均匀最短路下，热 hop（0→1、8→7、10→11、18→17 及其反向） 各被 14 条 (core, HA) 流穿过。系数 DAT = 14·2/8 = 3.50， RSP = 14·2/8 = 3.50， REQ = 14/8 = 1.75。

λ_DAT = λ_RSP = 1/3.50 = 2/7 ≈ 0.2857 txn/cycle/core， λ_REQ = 4/7（更松）。 每核 WriteData r* = 2·(2/7) = 4/7 ≈ 0.5714 flit/cycle， 全环 R* = 10·4/7 = 40/7 ≈ 5.7143 flit/cycle。 对分（4 条有向 hop）在 λ* 上 DAT/RSP 占用 5/7，打不满； 先满的是四条热 hop。

  1. 有限 tracker 本轮已排除。8 个 HA 各 256 表项，10 核 × 128 outstanding 往里灌，但 S0 重试 0.0 次/事务， 去掉 tracker 后吞吐仍是 4.5408、完成 λ 仍是 0.2270 —— 一点没变。前两轮它是主因（32 表项吞吐 2.3848、 128 表项 3.04）。
  2. 环受限本身只到 λ* 的 79.5%，这就是唯一的缺口。 无缓存 + 在环绝对优先：本地要上环必须 hop 空着；偏转 flit 再绕一圈（S0 偏转 1037 次）。 S0 有空就灌，不是按热 hop 的 2/7 均速注。贪心对撞加上 HA 抖动 0（无 HA think time），无限 tracker 的 makespan 88090 vs 下界 70000。

5.1 把 S1 调到失败比变小，吞吐会怎样

S1 没有“按方向压失败比”的旋钮，只有节点 AIMD。 热侧失败多 → 等级高 → 先砍的是已经挤不上去的核。

官方本轮： S1 失败比没有变小 （最大 2.53 vs S0 的 2.59）， 吞吐 -0.2%，完成 λ 仍远低于 2/7。 失败比变小不会把核吞吐送到 λ*。 绝对失败次数下降，多半只是注得更少。

5.2 官方 K=20000：把失败比压到 < 2

这项研究是 ha_track = 32 时代跑的独立 study （results/ring2_s1_dirbal.json，本轮未重跑）。 它的绝对吞吐（1.36–1.94）属于那个工作点； 可迁移的结论是方向失败比压不到 < 2 这条定性判断。
