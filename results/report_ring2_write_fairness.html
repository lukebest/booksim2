无缓存环上的 per-core 写带宽公平性

本次只跑 1 个 plane / 1 条 ring、均匀 tiled 写、 S0 与 S1。REQ / RSP / DAT 上下环口独立。 每 core 20000 笔 WriteNoSnp （请求量 ×10），每笔 2 个 WriteData flit。 HA 回 RSP / Comp 时延 0（无 HA think time） 拍。

结论

  1. 三通道链路独立。makespan 下界改由最忙 DAT/RSP hop 决定（bound 70000，port 50000 已松）。 Hop 理想全环 WriteData R* = 40/7 ≈ 5.714。
  2. tracker 从 32 加到 128：缓解了，但还没解除。 S0 吞吐 2.3848 → 3.04 flit/cycle （+27%）， 重试 0.602 → 0.1078 次/事务， 延迟 p50 = 59789。
    但峰值占用正顶在 128 个表项（= ha_track）， 而无限 tracker 参照要用到 195 个、吞吐 4.5408 —— 本轮只到它的 67%。 completer 表项仍在削带宽，只是从削一半变成削三分之一。 K = 20000 才暴露这一点：K = 4000 的短探测里 128 就够了（见 3.2.2）， 按短跑定 tracker 尺寸会低估。
  3. S1 相对 S0 吞吐 -1.2%，max/min 1.0014 → 1.002。 源端限速略减 RetryAck，帮不上 hop 理想。
  4. 缺口分两层，都不是缓存。S0 吞吐是 hop 理想 R* 的 53%： 先被无缓存环的上环饥饿削到 4.5408 （在环 flit 绝对优先，核只能挤进空隙；把 eject / inject / dir 各级缓存单独放宽都只动 ±1%），再被 128 个表项削到 3.04。见 3.2.2 与 4.5。
  5. 上环失败比大 ≠ 访存不均衡。失败比是同一核 CW/CCW 失败次数比， 不是失败率。8 个 HA 收包相等；本轮核间写带宽也齐。 它是邻 mem = 1 的核在热 hop 上打不进去的症状。见 4.3.2。
  6. 官方 K 上没有一组 S1 参数让所有核失败比都 < 2。 最接近是 dir_split + harsh（2.07，仍有 C0/C8）。 各核写带宽仍是一条平线，只比默认 S1 低约 4%。见 5.2。

1.2 协议：CHI WriteNoSnp 四拍握手

一笔写 = REQ → DBIDResp → WriteData×2 → Comp。 per-core 写带宽 = 争用窗口内成功上环的 WriteData flit / cycle。

1.2.1 写激励

地址走 tile × 64KB + (i mod 16) × 4KB，interleave 已均衡。 completer 侧每条 RSP（DBIDResp / RetryAck / Comp）独立抽 0（无 HA think time） 拍；同一笔事务在 S0 / S1 抽到同一份时延。 本轮 1 plane、K = 20000。

跑数前的预测（置信度 0.55）： 单平面、请求量 ×10、DBIDResp/RetryAck/Comp 各抽 U{4..64} 的均匀 tiled 写：成功上环仍按最短路接近 1:1；失败次数比双平面更偏，邻 mem 少的核失败比 ≥ 2；S1 两边一起限速，改不了方向比，吞吐低于 S0。 证伪：成功比 ≥ 2，或所有核失败比仍 < 2（与双平面一样），或 S1 吞吐不低于 S0
总线时延 30 拍的预测（置信度 0.7）：拥塞总线时延改为 30 拍（控制窗口 64 的一半）后，S1 用的是更旧的拥塞等级；上一轮总线=1 时 S1 已几乎等于 S0，更晚的反馈再拉开吞吐的空间很小。CW/CCW 失败比仍由邻 mem 几何决定，S1 改不了。 证伪：S1 吞吐相对 S0 掉超过 2%，或失败偏的核/方向翻面
对照：S1 总线实测 30 拍。
三通道链路独立的预测（置信度 0.6）：REQ/RSP/DAT 上下环口拆开后，端口不再叠三 VC；均等最短路的上限改由最忙 DAT/RSP hop 决定，λ*=2/7，全环 WriteData R*=40/7≈5.714。S0 仍受在环优先，到不了这条线，但应明显高于共用端口时的 2.67。位置效应更明显；S1 按窗口×3 放大预算后仍接近 S0。 证伪：S0 吞吐仍 ≤ 2.8，或 bound 仍由合并端口的 75000 决定
对照：per_vc_ports=True，bound=70000（link 70000 / port 50000），S0 吞吐 3.04，max/min 1.0014。
HA RSP 时延 = 0 的预测（置信度 0.6）：HA 回 RSP / Comp 的 think time 从 U{4..64}（均值 34 拍/条，一笔写至少 DBID+Comp 两条 ≈ 68 拍）改成 0。上一轮 T_hold ≈ 191 拍、R=2.41、retry/txn=0.57，其中一块就是这段 completer 等待。去掉之后 32 个 tracker 周转加快，retry 应下降，S0 吞吐应往无缓存环平台（上一轮无限 tracker ≈ 4.51）靠。32 tracker 未必完全松绑（68 拍只是 T_hold 的一部分），但差距应明显收窄。无限 tracker 平台本身不应大变：HA 时延不是环的限制。 证伪：S0 吞吐仍 ≤ 2.6（HA 时延不在关键路径上），或 retry/txn 仍 ≥ 0.50
对照：HA RSP 0（无 HA think time），S0 吞吐 3.04，retry/txn 0.1078。
50 拍窗 Jain 主指标的预测（置信度 0.75）：公平性主指标改成：50 拍宽的窗内对 10 个核的写带宽算 Jain，再对竞争窗口内的所有箱取平均。S0 总写带宽 ≈ 2.25 flit/cycle，摊到 10 个核上每核每箱只有约 0.225 × 50 ≈ 11 个 flit，因此这个指标会被计数噪声主导：等概率多项分布的零模型本身就只有 1/(1 + var/mean²) ≈ 1/(1 + 10.2/128) ≈ 0.926。上一轮 128 拍分箱已看到实测 max/min 低于零模型（亚泊松），所以实测均值应落在零模型之上、1.0 之下。结论不应改变：仍是采样粒度而非核间不公平。 证伪：jain_bin_mean 低于同窗零模型的 null_jain，或落到 0.90 以下 —— 那说明 50 拍尺度上存在真实的核间不公平，而不是抽样波动
对照：jain_bin_mean = 0.97618，零模型 0.94041，ratio 1.03803；每核每箱 15.23 flit，2624 个箱（详见 3.3）。
ha_track = 128 的预测（置信度 0.8）：ha_track 32 → 128，跨过 tracker 扫描找到的拐点。上一轮 32 tracker 下 S0 = 2.385 flit/cycle、retry/txn = 0.63，而短探测里 128 给出 4.424、retry/txn = 0.003，无限 tracker 平台是 4.498。所以预期：吞吐接近翻倍并贴上无缓存环平台，重试基本归零，makespan 从 16.8 万降到 9 万附近，而 s0_unbounded 参照与 S0 的差距收到几个百分点以内 —— 瓶颈从 completer 表项换成上环饥饿。公平性主指标应仍达标但数值上移：吞吐翻倍使每箱 flit 数从 11.9 涨到约 22，零模型地板随之从 0.929 抬到约 0.961，实测约 0.98，ratio 仍在 1.02 附近。整份报告的主线会因此改变：第 9、10 节讨论的重试浪费不再是主要损失。 证伪：S0 吞吐仍 ≤ 3.0（128 表项仍不够，或别的东西在绑定），或 retry/txn > 0.05，或 ratio < 1.0（放开 tracker 反而制造出真实的核间不公平）
对照：预测被推翻。预测 S0 吞吐落在 [4.2, 4.7]，实测只有 3.04；预测 retry/txn ≤ 0.05，实测 0.1078；预测 makespan [85000, 95000]，实测 131580；预测与 ∞ tracker 参照差 ≤ 3.0%，实测差 -33.1%（参照 4.5408）。只有公平性那三项落在区间里（详见 3.3）。
错在哪：预测直接引用了 K = 4000 的短探测（那里 128 给出 4.424）。官方 K = 20000 下稳态拥塞更深，∞ 参照的峰值占用要 195 个表项，128 装不下，实测峰值就顶在 128。tracker 的拐点跟 K 有关，短跑会低估所需表项数。
对照。 8 个 mem 收到的 WriteData 完全一样（50000 / HA）。 S0 延迟 p50 = 59789，主指标 Jain@50拍 = 0.97618 ÷ 零模型 0.94041 = ratio 1.03803； 诊断项 max/min = 1.0014。 S1 吞吐 3.004（-1.2% vs S0 3.04）。 S0 上环方向高亮 3/10 个核 （成功偏 0，失败偏 3， 失败最大比 2.444）； S1 高亮 4/10 个核 （失败最大比 2.38）。 预测写在 meta.stimulus_forecast，对照写在 meta.belief_update，前者不改。

2. 指标：分箱 Jain（主）、max/min 与吞吐

  • 分箱 Jain（公平性主指标，进验收线）：把争用窗口切成 50 拍宽的箱，每箱内对 10 个 core 那一箱的 写带宽算一次 Jain，再对所有箱取平均。它回答「任一时刻各核是否均衡」。
  • 零模型与判定：50 拍内每核只有十来个 flit，纯计数噪声就让 Jain 到不了 1.0，而且这个地板随吞吐移动，所以绝对阈值没有意义。 把每箱总数 N 等概率撒到 n 个核上有 E[J] ≈ N/(N+n−1)，逐箱平均即 jain_bin_null；判定用比值 ratio = 实测/零模型 ≥ 1.0，含义是至少和完全公平的仲裁一样齐。 本轮 S0 = 0.97618 / 零模型 0.94041 = ratio 1.03803。
  • max/min（整窗）：降为诊断项，不进验收线。它仍然有用， 因为分箱 Jain 是二次指标、看不见个别核被饿死，而 max/min 直接读最坏的核。 均匀写下各方案的分箱 Jain 差异小于噪声（S0 0.97618 vs S1 0.97606）， 这是均匀写本来就公平的正确反映；流量不均时它分得很开。
  • 吞吐：公平性可以靠把所有人一起压慢买到，所以必须一起报。

验收线：分箱 Jain ≥ 同窗零模型且吞吐相对基线不下降超过 1%。

3.2 全环总写带宽的理论值，以及实测随时间的曲线

三条 VC 各有自己的上 / 下环端口，所以端口不再是最紧的资源， 反而是最忙那条 dat 链路绑定：14 对 (core, mem) 的 WriteData 要压在同一段 hop 上，每对每笔写 2 个 flit。

热 hop 上的 dat：每笔写占 14 × 2 ÷ 8 = 3.50 个 hop-slot，故 λ* = 1/3.50 = 0.2857 txn/cycle/核。
全环理论总写带宽 R* = 10 × 2 × 0.2857 = 5.714 flit/cycle = 366 B/cycle。
交叉校验：总 WriteData 400000 flit ÷ makespan 下界 70000 拍 = 5.714，与上式一致。
端口界这次松得多（port_lb 50000 拍，等价 8.0 flit/cycle）—— 这正是三 VC 不共享端口带来的变化。

3.3 各核瞬时带宽均衡度（主指标）

指标定义：把竞争窗口 [0, t_fair] 切成宽度 50 拍的箱，在每一个箱内对 10 个 core 的写带宽 （= 该箱内各核 WriteData flit 数）算一次 Jain 指数，再对所有箱取平均。
只统计完整落在竞争窗口内的箱：过了 t_fair 就有核已经跑完自己的配额， 那里的 0 是没活干，不是被饿死。
判定：对照同窗零模型的比值 ratio ≥ 1.0（见 2.1）。

S0 基线：Jain@50拍 = 0.97618， 零模型 0.94041，ratio = 1.03803 （2624 个箱，每核每箱平均 15.23 个 flit；p05 0.9522、 最差箱 0.36885）。各方案的值见 3.1 汇总表。

那个 0.36885 的最差箱不是稳态：Jain < 0.8 的 18 个箱（占 0.7%） 全部落在 t ≥ 127850 的收尾段 —— 那里已有核清完自己的配额，只剩几个核在收尾。 中段没有这种箱，所以 p05 0.9522 比最小值更能代表分布。

为什么要按箱平均而不是直接看整段：闭环批量下每个核最终都要注入同样的 K×W 个 flit，把十几万拍平均掉之后 Jain = 1.0、 max/min = 1.0014，接近 1 有一半是配额相同这个算术事实 造成的，看不出瞬时行为。缩到 50 拍后箱内 max/min 平均 1.711、p95 2.286、最坏 13.0。

4.3.2 上环失败比大代表什么

「失败比」是同一个核两条出边的失败次数比 max(CW, CCW) / min，不是失败率。 黄底仍是比 ≥ 2 且该侧合计 ≥ 50。

S0 各核失败率其实都差不多（31%–33%）。 大的是方向比：成功比最大 1.07，失败比最大 2.44。 S0 失败偏的核 C0、C8、C18， S1 为 C0、C8、C10、C18。

不会造成 8 个 mem 收写不均。 地址 interleave 已均衡，本轮 HA 收到的 WriteData 全部相同（50000 / HA）。 本轮有限 tracker 下，也不会造成核间写带宽不均 （S0 max/min = 1.0014）。 有限 tracker 的重试反压把十个核一起压住。 环成为瓶颈时会：无限 tracker 下 max/min = 1.0104， 带宽与邻 mem 数 r = 0.8129。 失败比大的核就是邻 mem = 1 的那些核。 失败比大 = 这一侧出 hop 常被在环 flit 占着，本地尝试打不进去； 它是位置效应的症状，不是 mem 收包不均的原因。 本研究是纯写；读的 CompData 走反向同一组热 hop，机制相同。

为什么失败比会很大

  1. 最短路确定。N9 / N19 不接 HA，C10 的近端在 CW（M11）， C18 在 CCW（M17）。成功次数已经按这个需求偏到约 1.07。
  2. 偏的那一侧正好是全环最热的 hop（0→1、8→7、10→11、18→17）， 各被 14/80 条 (core, HA) 流穿过。
  3. 在环 DAT / RSP 有绝对优先，本地注入只能等空槽。 热侧是「尝试更多 × 成功率更低」，成功比仍约 1.07， 失败比被放大到 ≥ 2。两侧都是 mem 的核（如 C4 / C14）失败比 ≈ 1。

S1 改的是节点总预算，不改最短路，也不改在环优先， 所以失败比还在，只是换了一批核。

4.4 回到有限 tracker（128 个表项）

吞吐相对无限 tracker -33.1%， max/min 从 1.0104 到 1.0014， 重试 0.1078 次/事务。 ∞ 参照的峰值占用是 195 表项， 本轮 ha_track = 128 装不下 （实测峰值就顶在 128），所以它还在削带宽。
但它已经不再盖住几何：重试从上一轮 32 表项的 0.602 次/事务降到 0.1078， retry churn 小了一个量级，上面那套（环受限）的归因基线上也读得出来。

4.5 理想拥塞控制下的注入率（三 VC 链路独立）

REQ / RSP / DAT 的有向 hop 各有一份 σ=1 信用，互不占槽。 一笔事务仍要三条腿都走完，所以事务率受三张平面里最紧的那张限制： λ ≤ min(λ_REQ, λ_RSP, λ_DAT)。 本小节不把三 VC 叠进同一个上下环口。 λ* 是完成事务率，不是含重试的 REQ 上环次数。

均匀最短路下，热 hop（0→1、8→7、10→11、18→17 及其反向） 各被 14 条 (core, HA) 流穿过。系数 DAT = 14·2/8 = 3.50， RSP = 14·2/8 = 3.50， REQ = 14/8 = 1.75。

λ_DAT = λ_RSP = 1/3.50 = 2/7 ≈ 0.2857 txn/cycle/core， λ_REQ = 4/7（更松）。 每核 WriteData r* = 2·(2/7) = 4/7 ≈ 0.5714 flit/cycle， 全环 R* = 10·4/7 = 40/7 ≈ 5.7143 flit/cycle。 对分（4 条有向 hop）在 λ* 上 DAT/RSP 占用 5/7，打不满； 先满的是四条热 hop。

  1. 有限 tracker 仍是一半原因。8 个 HA 各 128 表项，10 核 × 128 outstanding 往里灌，S0 重试 0.1078 次/事务。 理想模型没有 RetryAck / PCrd / 重发 REQ。 去掉 tracker 后吞吐从 3.04 升到 4.5408、 完成 λ 从 0.1520 升到 0.2270 （仍只占 λ* 的 79.5%）。 上一轮 32 表项时更狠：吞吐只有 2.3848、 重试 0.602 次/事务。
  2. 另一半：环受限本身也只到 λ* 的 79.5%。 无缓存 + 在环绝对优先：本地要上环必须 hop 空着；偏转 flit 再绕一圈（S0 偏转 567 次）。 S0 有空就灌，不是按热 hop 的 2/7 均速注。贪心对撞加上 HA 抖动 0（无 HA think time），无限 tracker 的 makespan 88090 vs 下界 70000。
  3. S1 不是理想 CC。按节点、按窗口失败次数做 AIMD， 不按 hop 做 max-min，也不能在环上留槽。 预算上限 192 flit / 64 拍 ≈ 3 flit/cycle/核， 高于理想自有流量 3λ* ≈ 0.86。 它只是略减 Retry（0.1116 vs 0.1078）， 完成 λ 仍是 0.1502。总线 30 拍 < 窗口 64， 到不了“按热 hop 配额”。
