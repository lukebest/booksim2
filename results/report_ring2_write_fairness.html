无缓存环上的 per-core 写带宽公平性

workload：10 个 AI core 对 8 个 memory 节点做均匀写，每 core 2000 笔 WriteNoSnp、每笔 4 个 WriteData flit （每 core 8000 个数据 flit，共 20000 笔事务）。 节点 9、19 既不是 memory 也不是 AI core。

结论

  1. 均匀写流量确实存在位置相关的带宽失衡。S0 基线的 Jain = 0.99629，最快 / 最慢 = 1.176， 最慢 0.54863 vs 最快 0.64516 flit/cycle。 需求完全对称（每个 core 发一样多、目的地分布一样）， 差异纯粹来自节点在环上的位置。
  2. 根因是“身边有几个 mem”，不是“离 mem 多远”。 9 和 19 在环上正好对顶，把这一对从 memory 里去掉之后， 每个 core 到 8 个 mem 的平均跳数仍然全部等于 5.0 跳， r(带宽, 平均跳数) = 0.0，没有解释力。 真正决定带宽的是紧邻的 mem 个数： r = 0.9651（Spearman 0.8528）。 C0、C8、C10、C18 各只有 1 个相邻 mem（另一侧正对着非终端的 9 或 19）， 带宽全部 ≤ 0.56323；其余 C2、C4、C6、C12、C14、C16 两侧都是 mem，带宽全部 ≥ 0.61524。
  3. S1（拥塞等级 + AIMD）不但没修好，还把情况弄得更差。 Jain 0.99629 → 0.99217， max/min 1.176 → 1.3673， 吞吐 -17.0%。三条失效机理都被数据证实：max 聚合保比例、 差值规则惩罚受害者、源端限速在“在环优先”下造不出槽位。
  4. S15（最大最小公平份额 + 上游注入预约）基本解决问题。 Jain → 0.99992，max/min → 1.03， 每 core 带宽收敛到 0.57258 ~ 0.58975 的窄区间， 吞吐代价 -1.1%。跨 3 个随机种子： Jain 0.99950 ~ 0.99992、max/min 1.030 ~ 1.073、吞吐差 -1.1% ~ -2.6%。 对照验收线（Jain ≥ 0.98、max/min ≤ 1.05、吞吐差 ≤ 1%）， 按最坏种子判定：达成 Jain ≥ 0.98；未达成 max/min ≤ 1.05、吞吐差 ≤ 1%—— 公平性目标稳定成立（max/min 从 1.13~1.18 收到 1.03~1.07）， 但拉平最慢 core 要付 1%~3% 的吞吐，没能同时守住 1% 的吞吐预算。
  5. 全程严格无缓存。所有方案的 n_inring_blocked = 0、max_inring_hold = 0： S15 的预约只压制上游注入，从不停住已经在环上的 flit， 因此不需要在环上增加任何缓冲。

1.2 协议：CHI WriteNoSnp 四拍握手

1.3 前提：环是无缓存的，在环流量绝对优先

_launch 从不阻塞已在环上的 flit，只占用槽位；本地注入由 _can_board 拒绝——要么该有向 hop 的这条 VC 被占，要么 arr_set 显示 σ 拍内有在环 flit 即将到达。

在环流量先于本地注入预定槽位。一个节点想上环， 必须等到一个没有任何过路 flit 经过的空拍。 关键推论：源端限速无法凭空造出槽位——让上游少发， 让出来的空拍会被下一个过路 flit 顺手拿走。这决定了第 5 节 S1 为什么失败。

2. 公平性指标：Jain 指数怎么算、怎么读

设 n 个 core 实测到的写带宽为 x1, …, xn。 Jain 公平性指数定义为

J(x) = ( Σi=1..n xi )2  /  ( n · Σi=1..n xi2 )

即算术平均的平方除以二次平均的平方： J = x̄2 / (x̄2 + s2)， 其中 s2 是（有偏）方差。由此得到三条性质：

  • 取值范围 1/n ≤ J ≤ 1。全部相等时 J = 1； 只有一个 core 拿到全部带宽时 J = 1/n（本研究 n = 10， 下限 0.1）。
  • 与量纲和规模无关：所有 xi 同乘一个常数 J 不变。 所以整体降频、整体限速都不改变 Jain——这正是第 5 节里 S1“等比缩小、Jain 不动”的数学原因。
  • 可读作“有效公平份额数”：J·n 约等于“相当于几个 core 在平分带宽”。

与变异系数的关系是 J = 1 / (1 + CV2)， CV = s / x̄ 就是表里的 CoV 列。 所以 CoV 与 Jain 是同一个信息的两种写法：CoV = 0 ⟺ J = 1。

为什么还要同时看 max/min：Jain 是二次指标， 被多数节点主导，少数被饿死的节点对它影响有限。 10 个 core 里 9 个完全均等、剩下 1 个只有其余的 1/10， Jain 仍有 0.9191，而 max/min 已经是 10。 Jain 看整体形状，max/min 看最坏个体，两个都作为验收条件。

4.1 先排除“离 mem 更远”

9 和 19 在环上正好对顶，把这一对从 memory 里拿掉之后， 每个 core 到 8 个 mem 的平均跳数全部等于 5.0 跳， 连距离的多重集分布都只是重排。实测 r(带宽, 平均跳数) = 0.0，精确为零。 失衡的来源不是距离。

4.2 真正的判据：紧邻的 mem 有几个

写到隔壁 mem 的 flit 只占用一段链路就下环了；写到远处的 flit 要一路占着沿途每个节点的出向槽位，在“在环优先”下既更多地挡住别人， 也更多地被别人挡住。去掉 9、19 之后：

  • C2、C4、C6、C12、C14、C16 两侧都是 mem → 相邻 mem = 2， 2/8 = 25.0% 的写只走一跳；
  • C0、C8、C10、C18 有一侧正对非终端节点 → 相邻 mem = 1， 只有 12.5%。
带宽与相邻 mem 个数的相关系数 r = 0.9651（Spearman 0.8528）， 两档之间完全不重叠：相邻 2 个的最低带宽 0.61524 ＞ 相邻 1 个的最高带宽 0.56323。这就是位置依赖的确切形式。

4.3 落到硬件上：上环成功率

带宽与实测上环成功率的相关是 r = 0.973（Spearman 0.9483）， 与 hop_busy 失败次数强负相关； 与解析过路流量的相关很弱（r = 0.0191）—— 过路流量的总量差别不大，差别在于它什么时候正好卡住本地注入。 I-tag 类失败占比很小：_itag_blocks 只压制竞争的其他注入者， 对在环 flit 无效，所以它能限制饥饿时长，却造不出槽位。

5. S1：按规格实现的拥塞等级 AIMD

  • 拥塞检测：每节点每窗口分别统计上环失败（up）与 eject 偏转（down）的 total_fail 与 net_fail（只计纯粹由在环占用造成的失败）， 等级 = min(7, count // 8)。
  • 拥塞传递：CongestionBus 专用广播总线，不占环上 hop， 延迟 1 拍。
  • 拥塞反馈：每节点维护自己的通路节点表，对该集合取 max。
  • 流量控制：最终等级 = level_of(own_total_fail − max_received_net_fail)；罚则 budget ← max(min, ⌊budget·α⌋)， α = 0.75 / 0.5 / 0.25；奖励 budget ← min(window, budget + β)， β = 16 / 8 / 2。

5.1 结果：既没拉平，又欠吞吐

S1 把 Jain 从 0.99629 降到 0.99217， max/min 从 1.176 升到 1.3673， 吞吐 -17.0%。全部扫描点都没有同时改善公平性和吞吐。

5.2 为什么会这样

(a) max 聚合保住了比例。共享同一条通路的 core 收到同一个等级， 于是乘以同一个 α。等比缩小不改变贫富比值——这正是第 2 节 “Jain 与规模无关”的直接后果：预算曲线整体下移，Jain 不动。

(b) 差值规则把信号搞反了。被饿死的 core own_total_fail 很高；而占优的 core 正在赢， 它的 net_fail 很低，于是受害者收到的 max_received_net_fail 很小、差值很大 → 受害者惩罚自己；赢家差值 ≈ 0，继续 +β。 这是放大不公平的正反馈。

(c) 源端速率造不出槽位。在环优先是绝对的，被限速的 core 让出的空拍立刻被过路 flit 吃掉，被饿死的 core 一无所获。 所以 S1 只是把总量压下去。

6. S15：最大最小公平份额 + 槽预约

保留专用总线和窗口结构，换掉聚合什么，并加一个仲裁钩子。

  • 检测：额外记录成功上环数、累计成功数与 active 标志。
  • 传递：同一条总线多播 (等级, 本窗口成功数, 累计成功数, active, 各出向公平份额)。
  • 反馈：用最大最小公平份额替代 max-of-levels。每个共享资源 （有向 hop、以及目的 mem 的 leave 端口）按观测到的吞吐峰值作为容量， 除以其上的活跃竞争者，广播一个份额；节点取自己路径上所有资源份额的最小值。 容量取实测峰值而非理论值，回路因此自校准，不会把吞吐一路压下去。
  • 控制：AIMD 跟踪这个目标，并按累计欠账而非瞬时速率修正， 避免开局阶段的抢占决定全局。
  • 槽预约（真正的修复）：落后于全环平均累计进度超过 reserve_gap 的节点，通过总线预约未来若干拍的 (plane, dir, VC) 槽；上游节点不得注入会在预约窗口内到达该槽的 flit。资格用全环累计量判定而不是各自的本地目标——按本地判定时几乎 每个节点都认为自己落后，预约互相抵消，全环白白付出上万次让路。
  • 只在真的不公平时介入：总线上的累计进度离散度低于 fair_tol 时控制器完全不接管，公平的场景下零代价。
预约只压制注入，从不停住已经在环上的 flit， 所以不需要任何缓冲：n_inring_blocked 与 max_inring_hold 全程为 0，无缓存前提没有被偷偷放弃。

6.1 结果

Jain 0.99629 → 0.99992， max/min 1.176 → 1.03， 每 core 带宽收敛到 0.57258 ~ 0.58975， 吞吐 -1.1%。

吞吐的这点损失来自预约压制上游注入时留下的空拍。 它换来的是最慢 core 的带宽从 0.54863 抬到 0.57258 （1.04 倍）。
