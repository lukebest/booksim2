无缓存环上的 per-core 写带宽公平性

本次只跑 1 个 plane / 1 条 ring、均匀 tiled 写、 S0 与 S1。REQ / RSP / DAT 上下环口独立。 每 core 20000 笔 WriteNoSnp （请求量 ×10），每笔 2 个 WriteData flit。 HA 回 RSP / Comp 时延 U{4..64} 拍。

结论

  1. 三通道链路独立。makespan 下界改由最忙 DAT/RSP hop 决定（bound 70000，port 50000 已松）。 Hop 理想全环 WriteData R* = 40/7 ≈ 5.714。
  2. 有限 tracker 现在才是实测瓶颈。S0 吞吐 2.4101 flit/cycle，max/min 1.0013，重试 0.5689 次/事务， 延迟 p50 = 85557。 无限 tracker 参照吞吐 4.5136、max/min 1.0123 （峰值占用 213 表项）。 端口拆开让 REQ 更快堆到 HA，32 表项把大家一起压住，所以看起来更公平、吞吐更低。
  3. S1 相对 S0 吞吐 -0.2%，max/min 1.0013 → 1.0014。 源端限速略减 RetryAck，帮不上 hop 理想。
  4. 完成事务率远低于 λ* = 2/7。S0 / S1 只有理想的约 33–34%； 含重试的 REQ 上环更高，多的是重发。无限 tracker 也只到约 61%。 见 4.5。
  5. 上环失败比大 ≠ 访存不均衡。失败比是同一核 CW/CCW 失败次数比， 不是失败率。8 个 HA 收包相等；本轮核间写带宽也齐。 它是邻 mem = 1 的核在热 hop 上打不进去的症状。见 4.3.2。
  6. 官方 K 上没有一组 S1 参数让所有核失败比都 < 2。 最接近是 dir_split + harsh（2.07，仍有 C0/C8）。 各核写带宽仍是一条平线，只比默认 S1 低约 4%。见 5.2。

3.2 全环总写带宽的理论值，以及实测随时间的曲线

三条 VC 各有自己的上 / 下环端口，所以端口不再是最紧的资源， 反而是最忙那条 dat 链路绑定：14 对 (core, mem) 的 WriteData 要压在同一段 hop 上，每对每笔写 2 个 flit。

交叉校验：总 WriteData 400000 flit ÷ makespan 下界 70000 拍 = 5.714，与上式一致。
端口界这次松得多（port_lb 50000 拍，等价 8.0 flit/cycle）—— 这正是三 VC 不共享端口带来的变化。

4.3.2 上环失败比大代表什么

「失败比」是同一个核两条出边的失败次数比 max(CW, CCW) / min，不是失败率。 黄底仍是比 ≥ 2 且该侧合计 ≥ 50。

S0 各核失败率其实都差不多（24%–27%）。 大的是方向比：成功比最大 1.20，失败比最大 2.69。 S0 失败偏的核 C10、C18， S1 为 C10、C18。

不会造成 8 个 mem 收写不均。 地址 interleave 已均衡，本轮 HA 收到的 WriteData 全部相同（50000 / HA）。 本轮有限 tracker 下，也不会造成核间写带宽不均 （S0 max/min = 1.0013）。 32 表项把十个核一起压住。 环成为瓶颈时会：无限 tracker 下 max/min = 1.0123， 带宽与邻 mem 数 r = 0.9366。 失败比大的核就是邻 mem = 1 的那些核。 失败比大 = 这一侧出 hop 常被在环 flit 占着，本地尝试打不进去； 它是位置效应的症状，不是 mem 收包不均的原因。 本研究是纯写；读的 CompData 走反向同一组热 hop，机制相同。

为什么失败比会很大

  1. 最短路确定。N9 / N19 不接 HA，C10 的近端在 CW（M11）， C18 在 CCW（M17）。成功次数已经按这个需求偏到约 1.20。
  2. 偏的那一侧正好是全环最热的 hop（0→1、8→7、10→11、18→17）， 各被 14/80 条 (core, HA) 流穿过。
  3. 在环 DAT / RSP 有绝对优先，本地注入只能等空槽。 热侧是「尝试更多 × 成功率更低」，成功比仍约 1.20， 失败比被放大到 ≥ 2。两侧都是 mem 的核（如 C4 / C14）失败比 ≈ 1。

S1 改的是节点总预算，不改最短路，也不改在环优先， 所以失败比还在，只是换了一批核。

4.4 有限 tracker

max/min 从 1.0123 到 1.0013， 吞吐相对无限 tracker -46.6%。 峰值占用 213 表项； 有限 tracker 下重试 0.5689 次/事务。

4.5 理想拥塞控制下的注入率（三 VC 链路独立）

REQ / RSP / DAT 的有向 hop 各有一份 σ=1 信用，互不占槽。 一笔事务仍要三条腿都走完，所以事务率受三张平面里最紧的那张限制： λ ≤ min(λ_REQ, λ_RSP, λ_DAT)。 本小节不把三 VC 叠进同一个上下环口。 λ* 是完成事务率，不是含重试的 REQ 上环次数。

均匀最短路下，热 hop（0→1、8→7、10→11、18→17 及其反向） 各被 14 条 (core, HA) 流穿过。系数 DAT = 14·2/8 = 3.50， RSP = 14·2/8 = 3.50， REQ = 14/8 = 1.75。

λ_DAT = λ_RSP = 1/3.50 = 2/7 ≈ 0.2857 txn/cycle/core， λ_REQ = 4/7（更松）。 每核 WriteData r* = 2·(2/7) = 4/7 ≈ 0.5714 flit/cycle， 全环 R* = 10·4/7 = 40/7 ≈ 5.7143 flit/cycle。 对分（4 条有向 hop）在 λ* 上 DAT/RSP 占用 5/7，打不满； 先满的是四条热 hop。

4.5.1 为什么 S0 / S1 到不了 λ*

  1. 有限 tracker 是本轮主因。8 个 HA 各 32 表项，10 核 × 128 outstanding 往里灌。 S0 重试 0.5689 次/事务。理想模型没有 RetryAck / PCrd / 重发 REQ。去掉 tracker 后吞吐从 2.4101 升到 4.5136， 完成 λ 从 0.1205 升到 0.2257（仍只占 λ* 的 79.0%）。
  2. 即使环受限也只有约 61%。无缓存 + 在环绝对优先：本地要上环必须 hop 空着；偏转 flit 再绕一圈（S0 偏转 234 次）。 S0 有空就灌，不是按热 hop 的 2/7 均速注。贪心对撞加上 HA 抖动 U{4..64}，无限 tracker 的 makespan 88622 vs 下界 70000。
  3. S1 不是理想 CC。按节点、按窗口失败次数做 AIMD， 不按 hop 做 max-min，也不能在环上留槽。 预算上限 192 flit / 64 拍 ≈ 3 flit/cycle/核， 高于理想自有流量 3λ* ≈ 0.86。 它只是略减 Retry（0.5636 vs 0.5689）， 完成 λ 仍是 0.1203。总线 30 拍 < 窗口 64， 到不了“按热 hop 配额”。

5. S1

拥塞总线延迟 30 拍，控制窗口 64 拍。 端口拆开后 S1 的节点预算上限按 VC 数放大（窗口 × 3），避免把三通道独立注入口误限成 1 flit/cycle。 反馈只在窗口边界写入并在下一窗口边界读取： 30 < 64，所以 30 拍与 1 拍都在下一次 AIMD 之前送到， 本轮 S1 与总线=1 时逐拍相同（makespan 166305）。

5.1 把 S1 调到失败比变小，吞吐会怎样

S1 没有“按方向压失败比”的旋钮，只有节点 AIMD。 热侧失败多 → 等级高 → 先砍的是已经挤不上去的核。

官方本轮： S1 失败比没有变小 （最大 2.72 vs S0 的 2.69）， 吞吐 -0.2%，完成 λ 仍远低于 2/7。 失败比变小不会把核吞吐送到 λ*。 绝对失败次数下降，多半只是注得更少。
