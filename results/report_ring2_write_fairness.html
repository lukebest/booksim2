无缓存环上的 per-core 写带宽公平性

本次只跑 1 个 plane / 1 条 ring、均匀 tiled 写、 S0 与 S1。上环两方向共用 8 深 FIFO，其后每向一个 inject Q；上环 / 下环各 1 flit/cycle/node，下环两写一读；路由按链路时延最短（平局再比跳数，再 CW）。 每 core 20000 笔 WriteNoSnp （请求量 ×10），每笔 2 个 WriteData flit。 HA 回 RSP / Comp 时延 U{4..64} 拍。

结论

  1. 端口合并 + 共享上环缓冲。makespan 下界 75000（link 70000，port 75000）。理想 λ* ≈ 0.2667（端口 4/15 与 hop 2/7 取紧），全环 WriteData R* ≈ 5.333。
  2. 有限 tracker 现在才是实测瓶颈。S0 吞吐 2.5333 flit/cycle，max/min 1.001，重试 0.4288 次/事务， 延迟 p50 = 83484。 无限 tracker 参照吞吐 3.4783、max/min 1.0841 （峰值占用 47 表项）。 共享 FIFO 可能 HOL；有限 tracker 仍把各核一起压住。
  3. S1 相对 S0 吞吐 +3.5%，max/min 1.001 → 1.0014。 源端限速略减 RetryAck，帮不上 hop / 端口理想。
  4. 完成事务率远低于 λ* ≈ 0.2667。 S0 完成 λ 见 4.5。含重试的 REQ 上环更高，多的是重发。
  5. 上环失败比大 ≠ 访存不均衡。失败比是同一核 CW/CCW 失败次数比， 不是失败率。8 个 HA 收包相等；本轮核间写带宽也齐。 失败比 ≥ 2 的核是 C10、C18 （S0 最大 2.4）。见 4.3.2。

4.1 先排除“离 mem 更远”

到 8 个 mem 的平均跳数全部等于 5.0。r(带宽, 平均跳数) = 0.0。失衡的来源不是距离。

4.2 真正的判据：紧邻的 mem 有几个

  • C2、C4、C6、C12、C14、C16 两侧都是 mem → 相邻 mem = 2；
  • C0、C8、C10、C18 有一侧是非终端 → 相邻 mem = 1。
无限 tracker 上带宽与相邻 mem 个数 r = 0.9741 （Spearman 0.8528）。 有限 tracker 把这条链盖住：重试 0.4288 次/事务， max/min 从 1.0841 收到 1.001。

4.3 落到硬件上：上环成功率

带宽与上环成功率 r = 0.9944 （Spearman 0.9515）， 与解析过路流量 r = 0.0。 成功次数几乎按最短路 1:1 切开；不平衡出在失败次数—— 邻 mem = 1 的核失败集中在朝向仅剩那个 mem 的一侧。

4.3.2 上环失败比大代表什么

「失败比」是同一个核两条出边的失败次数比 max(CW, CCW) / min，不是失败率。 黄底仍是比 ≥ 2 且该侧合计 ≥ 50。

S0 各核失败率其实都差不多（33%–37%）。 大的是方向比：成功比最大 1.20，失败比最大 2.40。 S0 失败偏的核 C10、C18， S1 为 C10、C18。

不会造成 8 个 mem 收写不均。 地址 interleave 已均衡，本轮 HA 收到的 WriteData 全部相同（50000 / HA）。 本轮有限 tracker 下，也不会造成核间写带宽不均 （S0 max/min = 1.001）。 32 表项把十个核一起压住。 环成为瓶颈时会：无限 tracker 下 max/min = 1.0841， 带宽与邻 mem 数 r = 0.9741。 失败比大的核就是邻 mem = 1 的那些核。 失败比大 = 这一侧出 hop 常被在环 flit 占着，本地尝试打不进去； 它是位置效应的症状，不是 mem 收包不均的原因。 本研究是纯写；读的 CompData 走反向同一组热 hop，机制相同。

为什么失败比会很大

  1. 最短路确定。N9 / N19 不接 HA，C10 的近端在 CW（M11）， C18 在 CCW（M17）。成功次数已经按这个需求偏到约 1.20。
  2. 偏的那一侧正好是全环最热的 hop（0→1、8→7、10→11、18→17）， 各被 14/80 条 (core, HA) 流穿过。
  3. 在环 DAT / RSP 有绝对优先，本地注入只能等空槽。 热侧是「尝试更多 × 成功率更低」，成功比仍约 1.20， 失败比被放大到 ≥ 2。两侧都是 mem 的核（如 C4 / C14）失败比 ≈ 1。

S1 改的是节点总预算，不改最短路，也不改在环优先， 所以失败比还在，只是换了一批核。

4.4 有限 tracker

max/min 从 1.0841 到 1.001， 吞吐相对无限 tracker -27.2%。 峰值占用 47 表项； 有限 tracker 下重试 0.4288 次/事务。

4.5 理想拥塞控制下的注入率（hop 独立、端口合并）

REQ / RSP / DAT 的有向 hop 各有一份 σ=1 信用，互不占槽。 一笔事务仍要三条腿都走完，所以事务率受最紧的 hop 或端口限制。 λ* 是完成事务率，不是含重试的 REQ 上环次数。

均匀最短路下，热 hop（0→1、10→11、18→17、8→7） 各被 14 条 (core, HA) 流穿过。系数 DAT = 14·2/8 = 3.50， RSP = 14·2/8 = 3.50， REQ = 14/8 = 1.75。

热 hop 上 λ_hop = 1/3.50 = 0.2857（DAT/RSP）。三 VC 共用 1 个下环口时 HA leave 叠 REQ+WriteData，λ_port = 8/10 / (1+2) = 0.2667。λ* 取更紧的端口。 每核 WriteData r* = 2·λ* ≈ 0.5333 flit/cycle， 全环 R* ≈ 5.3333 flit/cycle。

4.5.1 为什么 S0 / S1 到不了 λ*

  1. 有限 tracker 是本轮主因。8 个 HA 各 32 表项，10 核 × 128 outstanding 往里灌。 S0 重试 0.4288 次/事务。理想模型没有 RetryAck / PCrd / 重发 REQ。去掉 tracker 后吞吐从 2.5333 升到 3.4783， 完成 λ 从 0.1267 升到 0.1739（仍只占 λ* 的 65.2%）。
  2. 无缓存 + 在环绝对优先。本地要上环必须 hop 空着；偏转 flit 再绕一圈（S0 偏转 47450 次）。 S0 有空就灌，不是按热 hop / 端口的 λ* 均速注。贪心对撞加上 HA 抖动 U{4..64}，无限 tracker 的 makespan 114999 vs 下界 75000。
  3. S1 不是理想 CC。按节点、按窗口失败次数做 AIMD， 不按 hop 做 max-min，也不能在环上留槽。 预算上限 64 flit / 64 拍 ≈ 1 flit/cycle/核， 高于理想自有流量 3λ* ≈ 0.80。 它只是略减 Retry（0.2912 vs 0.4288）， 完成 λ 仍是 0.1310。总线 30 拍 < 窗口 64， 到不了“按热 hop 配额”。

5. S1

拥塞总线延迟 30 拍，控制窗口 64 拍。 反馈只在窗口边界写入并在下一窗口边界读取： 30 < 64，所以 30 拍与 1 拍都在下一次 AIMD 之前送到， 本轮 S1 与总线=1 时逐拍相同（makespan 152623）。

5.1 把 S1 调到失败比变小，吞吐会怎样

S1 没有“按方向压失败比”的旋钮，只有节点 AIMD。 热侧失败多 → 等级高 → 先砍的是已经挤不上去的核。

官方本轮： S1 最大失败比 2.21 vs S0 的 2.40， 吞吐 +3.5%，完成 λ 仍远低于 λ*。 失败比变小不会把核吞吐送到 λ*。 绝对失败次数下降，多半只是注得更少。
