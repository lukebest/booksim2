无缓存环上的 per-core 写带宽公平性

本次只跑 1 个 plane / 1 条 ring、均匀 tiled 写、 S0 与 S1。REQ / RSP / DAT 上下环口独立。 每 core 20000 笔 WriteNoSnp （请求量 ×10），每笔 2 个 WriteData flit。 HA 回 RSP / Comp 时延 0（无 HA think time） 拍。

结论

  1. 三通道链路独立。makespan 下界改由最忙 DAT/RSP hop 决定（bound 70000，port 50000 已松）。 Hop 理想全环 WriteData R* = 40/7 ≈ 5.714。
  2. 有限 tracker 现在才是实测瓶颈。S0 吞吐 2.3781 flit/cycle，max/min 1.0011，重试 0.6337 次/事务， 延迟 p50 = 85898。 无限 tracker 参照吞吐 4.5332、max/min 1.007 （峰值占用 216 表项）。 端口拆开让 REQ 更快堆到 HA，32 表项把大家一起压住，所以看起来更公平、吞吐更低。 HA RSP 时延改成 0 之后吞吐几乎不动（见 3.2.3）：completer think time 不在关键路径上。
  3. S1 相对 S0 吞吐 +0.3%，max/min 1.0011 → 1.0013。 源端限速略减 RetryAck，帮不上 hop 理想。
  4. 完成事务率远低于 λ* = 2/7。S0 / S1 只有理想的约 33–34%； 含重试的 REQ 上环更高，多的是重发。无限 tracker 也只到约 61%。 见 4.5。
  5. 上环失败比大 ≠ 访存不均衡。失败比是同一核 CW/CCW 失败次数比， 不是失败率。8 个 HA 收包相等；本轮核间写带宽也齐。 它是邻 mem = 1 的核在热 hop 上打不进去的症状。见 4.3.2。
  6. 官方 K 上没有一组 S1 参数让所有核失败比都 < 2。 最接近是 dir_split + harsh（2.07，仍有 C0/C8）。 各核写带宽仍是一条平线，只比默认 S1 低约 4%。见 5.2。

1.2 协议：CHI WriteNoSnp 四拍握手

1.2.1 写激励

地址走 tile × 64KB + (i mod 16) × 4KB，interleave 已均衡。 completer 侧每条 RSP（DBIDResp / RetryAck / Comp）独立抽 0（无 HA think time） 拍；同一笔事务在 S0 / S1 抽到同一份时延。 本轮 1 plane、K = 20000。

2. 三个指标：分箱 Jain（主）、max/min 与吞吐

  • 分箱 Jain（公平性主指标）：把争用窗口切成 50 拍宽的箱， 每箱内对 10 个 core 那一箱的写带宽算一次 Jain， 再对所有箱取平均。它回答「任一时刻各核是否均衡」。 定义、零模型对照与结果见 3.3。
  • max/min（整个争用窗口）：方案比较与验收沿用它，因为它直接读 最坏的那个 core。分箱 Jain 是二次指标，在 50 拍尺度上又被计数噪声主导， 方案之间几乎不动（S0 0.95271 vs S1 0.95265），不能用来分辨方案。
  • 吞吐：公平性可以靠把所有人一起压慢买到，所以必须一起报。

验收线仍是 max/min ≤ 1.05 且吞吐相对基线不下降超过 1%。

3.2 全环总写带宽的理论值，以及实测随时间的曲线

三条 VC 各有自己的上 / 下环端口，所以端口不再是最紧的资源， 反而是最忙那条 dat 链路绑定：14 对 (core, mem) 的 WriteData 要压在同一段 hop 上，每对每笔写 2 个 flit。

热 hop 上的 dat：每笔写占 14 × 2 ÷ 8 = 3.50 个 hop-slot，故 λ* = 1/3.50 = 0.2857 txn/cycle/核。
全环理论总写带宽 R* = 10 × 2 × 0.2857 = 5.714 flit/cycle = 366 B/cycle。
交叉校验：总 WriteData 400000 flit ÷ makespan 下界 70000 拍 = 5.714，与上式一致。
端口界这次松得多（port_lb 50000 拍，等价 8.0 flit/cycle）—— 这正是三 VC 不共享端口带来的变化。

3.3 各核瞬时带宽均衡度（主指标）

指标定义：把竞争窗口 [0, t_fair] 切成宽度 50 拍的箱，在每一个箱内对 10 个 core 的写带宽 （= 该箱内各核 WriteData flit 数）算一次 Jain 指数，再对所有箱取平均。
只统计完整落在竞争窗口内的箱：过了 t_fair 就有核已经跑完自己的配额， 那里的 0 是没活干，不是被饿死。

S0 基线：Jain@50拍 = 0.95271 （3356 个箱，每核每箱平均 11.91 个 flit；p05 0.90738、 最差箱 0.2）。各方案的值见 3.1 汇总表。

那个 0.2 的最差箱不是稳态：Jain < 0.8 的 21 个箱（占 0.6%） 全部落在 t ≤ 600 的起步段和 t ≥ 165650 的收尾段 —— 前者还有核没发出第一笔 WriteData，后者已有核在清最后几个 flit。 中段没有这种箱，所以 p05 0.90738 比最小值更能代表分布。

为什么要按箱平均而不是直接看整段：闭环批量下每个核最终都要注入同样的 K×W 个 flit，把十几万拍平均掉之后 Jain = 1.0、 max/min = 1.0011，接近 1 有一半是配额相同这个算术事实 造成的，看不出瞬时行为。缩到 50 拍后箱内 max/min 平均 2.282、p95 4.0、最坏 16.0。

4.3.2 上环失败比大代表什么

「失败比」是同一个核两条出边的失败次数比 max(CW, CCW) / min，不是失败率。 黄底仍是比 ≥ 2 且该侧合计 ≥ 50。

S0 各核失败率其实都差不多（24%–28%）。 大的是方向比：成功比最大 1.19，失败比最大 2.80。 S0 失败偏的核 C10、C18， S1 为 C10、C18。

不会造成 8 个 mem 收写不均。 地址 interleave 已均衡，本轮 HA 收到的 WriteData 全部相同（50000 / HA）。 本轮有限 tracker 下，也不会造成核间写带宽不均 （S0 max/min = 1.0011）。 32 表项把十个核一起压住。 环成为瓶颈时会：无限 tracker 下 max/min = 1.007， 带宽与邻 mem 数 r = 0.7625。 失败比大的核就是邻 mem = 1 的那些核。 失败比大 = 这一侧出 hop 常被在环 flit 占着，本地尝试打不进去； 它是位置效应的症状，不是 mem 收包不均的原因。 本研究是纯写；读的 CompData 走反向同一组热 hop，机制相同。

为什么失败比会很大

  1. 最短路确定。N9 / N19 不接 HA，C10 的近端在 CW（M11）， C18 在 CCW（M17）。成功次数已经按这个需求偏到约 1.19。
  2. 偏的那一侧正好是全环最热的 hop（0→1、8→7、10→11、18→17）， 各被 14/80 条 (core, HA) 流穿过。
  3. 在环 DAT / RSP 有绝对优先，本地注入只能等空槽。 热侧是「尝试更多 × 成功率更低」，成功比仍约 1.19， 失败比被放大到 ≥ 2。两侧都是 mem 的核（如 C4 / C14）失败比 ≈ 1。

S1 改的是节点总预算，不改最短路，也不改在环优先， 所以失败比还在，只是换了一批核。

4.4 有限 tracker

max/min 从 1.007 到 1.0011， 吞吐相对无限 tracker -47.5%。 峰值占用 216 表项； 有限 tracker 下重试 0.6337 次/事务。

4.5 理想拥塞控制下的注入率（三 VC 链路独立）

REQ / RSP / DAT 的有向 hop 各有一份 σ=1 信用，互不占槽。 一笔事务仍要三条腿都走完，所以事务率受三张平面里最紧的那张限制： λ ≤ min(λ_REQ, λ_RSP, λ_DAT)。 本小节不把三 VC 叠进同一个上下环口。 λ* 是完成事务率，不是含重试的 REQ 上环次数。

均匀最短路下，热 hop（0→1、8→7、10→11、18→17 及其反向） 各被 14 条 (core, HA) 流穿过。系数 DAT = 14·2/8 = 3.50， RSP = 14·2/8 = 3.50， REQ = 14/8 = 1.75。

λ_DAT = λ_RSP = 1/3.50 = 2/7 ≈ 0.2857 txn/cycle/core， λ_REQ = 4/7（更松）。 每核 WriteData r* = 2·(2/7) = 4/7 ≈ 0.5714 flit/cycle， 全环 R* = 10·4/7 = 40/7 ≈ 5.7143 flit/cycle。 对分（4 条有向 hop）在 λ* 上 DAT/RSP 占用 5/7，打不满； 先满的是四条热 hop。

4.5.1 为什么 S0 / S1 到不了 λ*

  1. 有限 tracker 是本轮主因。8 个 HA 各 32 表项，10 核 × 128 outstanding 往里灌。 S0 重试 0.6337 次/事务。理想模型没有 RetryAck / PCrd / 重发 REQ。去掉 tracker 后吞吐从 2.3781 升到 4.5332， 完成 λ 从 0.1189 升到 0.2267（仍只占 λ* 的 79.3%）。
  2. 即使环受限也只有约 61%。无缓存 + 在环绝对优先：本地要上环必须 hop 空着；偏转 flit 再绕一圈（S0 偏转 234 次）。 S0 有空就灌，不是按热 hop 的 2/7 均速注。贪心对撞加上 HA 抖动 0（无 HA think time），无限 tracker 的 makespan 88238 vs 下界 70000。
  3. S1 不是理想 CC。按节点、按窗口失败次数做 AIMD， 不按 hop 做 max-min，也不能在环上留槽。 预算上限 192 flit / 64 拍 ≈ 3 flit/cycle/核， 高于理想自有流量 3λ* ≈ 0.86。 它只是略减 Retry（0.5918 vs 0.6337）， 完成 λ 仍是 0.1192。总线 30 拍 < 窗口 64， 到不了“按热 hop 配额”。
