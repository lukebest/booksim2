3D 堆叠 NoC：按 top die 分组的写带宽

bottom die 横环 4 cycle / 纵环 6 cycle / 挂接点转向 5 cycle。 每 core 请求数 = 800（closed batch，共 48,000 笔）， 每 core outstanding = 128（在途上限）， 每个 HA 跟踪表 16 项，超出回 RetryAck。 最长无拥塞写 RTT = 413 cycle。

k 和 outstanding 不是一回事。 k = 800 是每个 AI core 这一批要发的写请求总数。 outstanding = 128 是同时能挂在网上的笔数：一笔从 REQ 上环占到 Comp 回来。 S0 没有源端流控——只要该 core 还有 outstanding 空位、注入口当前 cycle ring 上有空 slot，就把下一条 REQ 发出；HA 跟踪表满回 RetryAck，那是完成方反压，不是源端控速。 S1 在同样的 outstanding + slot 条件之上，再加 AIMD 源端注入预算。

结论

  1. outstanding 设为 128。 无拥塞的 WriteNoSnp 往返 = REQ 去程 + DBID 回程 + WriteData 去程 （4 flit 流水，最后一拍比第一拍晚 3 cycle）+ Comp 回程。 最坏一对 (core 4, HA 231) 的去程 58 cycle、回程 147 cycle，合计 413 cycle。额度从 REQ 上环一直占到 Comp 回来。 窗口 128 小于最长 RTT 413，长路径上 core 会先把 128 个槽占满再等 Comp。 本批次每 core 800 笔，大于窗口 128，实测峰值占用 128，outstanding 上限已经打满——S0 能发出去的条件只剩 outstanding 空位和 ring slot。
  2. HA 跟踪表满了就 retry。S0 不另加源端控速，S1 才控速。 每个 HA 同时只能收 16 个请求；再来的 REQ 走 RetryAck → PCrdGrant → 重发 REQ，占真实 RSP/REQ 带宽。 S0 完成 48,000/48,000，makespan 35,269 cycle， RetryAck 37,236 次，有效并发是名义值的 22.1%； S1 完成 48,000/48,000，35,063 cycle， retry 37,257。 两个方案都排空，没有活锁、没有停在停滞检测器上。
  3. 按 top die 一组（10 个 AI core）看写带宽随时间的变化。 S0 组间完成量 max/min = 1.00， 组间 Jain 1.0000； S1 为 1.00 / 1.0000。 下图是各 group 写带宽随时间的曲线。
