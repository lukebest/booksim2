3D 堆叠 NoC 上的 per-core 写带宽公平性

拓扑：6 个 top die（每个 20 节点、双平面、 双向 full ring：10 个 AI core + 8 个 D2D bridge + 2 个非终端节点） + 48 条 D2D 链路 + 1 个 bottom die（96 个 HA，12 行 × 8 列； 6 条横向 + 8 条纵向单向 half ring）。 workload：60 个 AI core 均匀写 96 个 HA， 每 core 50 笔 WriteNoSnp、每笔 4 个 WriteData flit，共 3,000 笔事务；每 core outstanding 上限 128。

结论

  1. 最重要的一条：在这个拓扑上，路由策略的影响远大于任何流控方案。 按题目字面实现的 S0（每笔走最短路径、双平面负载均衡）， 在规定的 outstanding=128 下直接拥塞崩溃： 3,000 笔事务只完成 160 笔 （5%），且已有 core 的带宽掉到 0（max/min = ∞）。 换成维序路由（在目的列自己的 bridge 上跨 die，之后只走该列纵环， 一个横向跳都不走）——同一份硬件、同一个 workload、同样 outstanding： 全部完成，吞吐 2.185 txn/cycle， 达到理论下界的 95%。 即使给最短路径挑它自己最好的并发度（outstanding=16， 0.785 txn/cycle），维序路由在自己的最优点 （2.229 txn/cycle）仍然快 2.8 倍。 而且 S1、S16、S17 加在最短路径版本上全都救不回来（§5.1）， 因为流控只能决定“注入多少”，改变不了“流量往哪里挤”。
  2. 最短路径为什么反而更慢：它拿稀缺资源去换充裕资源。 bottom die 跳延迟 1 cycle，top die 环内 1~4 cycle， 所以“按时延最短”会诱导流量尽早跨到 bottom die、再用横环横向挪位， 甚至把纵环当作横环之间的过路通道。 但容量模型显示纵环才是全局瓶颈：每笔事务的写数据要在纵环上走 35.64 个 flit·跳， 而 top 环容量（480 条链路）相对需求过剩十倍以上。 结果最忙的一条纵向链路承担了平均值的 4.04 倍（3,000 flit， 全压在第 0 列），维序路由把它压到 1.59 倍。 注意维序路由的平均跳数其实更长 （14.93 vs 13.59 跳）， 却把下界抬高了 2.30 倍 ——决定性能的是负载均衡，不是路径长度。
  3. 修正计划中的一个预期：转向 FIFO 深度不是悬崖，4 flit 就够。 计划把“横↔纵转向 FIFO 深 4 flit”列为需要验证的风险项。 实测在维序路由下，深度 4 与深度 128 的吞吐只差 3.1% （2.149 → 2.216 txn/cycle）， 全部事务都能完成。此前观察到的“深度 4 活锁”其实是最短路径路由的热点， 不是缓冲不足：最短路径下把 FIFO 加深到 128 依然崩溃 （只完成 634 笔）。也就是说这里不需要为 bottom die 付大缓冲的代价。
  4. 公平性最便宜的解法根本不是流控，而是把 outstanding 从 128 调到 32。 这是本文最实用的发现。跨 3 个随机种子，维序路由下： outstanding=128 得到平均效率 93.5%、 Jain 0.93762、最差 max/min 3.1746； outstanding=32 得到平均效率 96.7%、 Jain 0.94847、最差 max/min 2.2727。 也就是说吞吐和公平性同时变好，而代价是零—— outstanding 上限本来就是一个已有的寄存器。 反过来说，题目规定的 128 把织物推过了最优点： 多出来的在途报文并不产生吞吐，只是变成互相阻塞的偏转流量。 并发度不是“越大越好、到某点崩溃”，而是存在一个真正的最优点 （16 以下欠载、32 附近最优、128 已经过载）。
  5. 把路由和并发度都调对之后，位置相关的失衡仍然存在。 维序路由、outstanding=128： Jain = 0.93635，max/min = 3.5088， 每核带宽 0.19064 ~ 0.6689 flit/cycle。 需求是完全对称的（每 core 发一样多、目的地分布一样）， 差异纯粹来自位置。
  6. 根因不是“top die 编号”——计划里的假设被数据否定。 计划预期带宽按 top die 编号（即纵环插入位置 1,2,8,9,15,16）单调排序。 实测 Spearman(die 编号, 带宽) = -0.0581， 几乎为零。真实结构是成对锯齿： 每个行间隙放两个相邻的挂接点，第二个永远在第一个的正下游。 在“在环优先”绝对优先的规则下，第二个挂接点注入时， 它要挤进的那条出边上已经载着第一个挂接点全部的写数据。 解析值把机理钉死了——成对的注入边负载相差恰好 48 个单位 （168↔216、144↔192、120↔168）， 而 48 = 12 HA × 4 flit = 一个 die 的完整写数据输出。 偶数 die 平均 0.55307、奇数 die 平均 0.35942，相差 1.54 倍； Spearman(成对次序, 带宽) = -0.8241， Spearman(注入边 DAT 负载, 带宽) = -0.7665。 而 core 在 top 环上的位置几乎没有影响（0.0887）—— top 环容量过剩，片内位置不构成瓶颈。
  7. S1（拥塞等级 + AIMD）方向正确、收益真实但有限，且代价不低。 Jain 0.93635 → 0.94549， max/min 3.5088 → 2.5641， 吞吐还略有改善（makespan 1373 → 1359）。 跨种子也稳定（最差 Jain 0.94549、 最差 max/min 2.7027），是三个流控方案里最可靠的。 但它需要一条专用广播总线（实测 5,544 次广播、 33,264 bit）和每源平均 140.6 项的受控节点表。而且一旦 outstanding 已经调到 32， S1 的增量就只剩 Jain 0.94847 → 0.95465 （最差 max/min 都是 2.2727）——几乎被“调寄存器”取代了。
  8. S16（接收端授权，Homa 式）在这个拓扑上无效，这是一个有价值的负面结论。 CHI 的 DBIDResp 确实是天然的 GRANT，完成端（HA）也确实坐在 瓶颈纵环上，看起来是理想的控制点。但实测在 overcommit=32 下 2,997 笔授权是立即发出的，只有 3 笔真正被节流—— 预算从来没有绑定，所以结果与基线基本相同 （Jain 0.93839 vs 0.93635）。 把 overcommit 压小到会绑定的程度，公平性反而急剧恶化 （overcommit=4：Jain 0.53884、 max/min 50.0）。 原因是控制点不在瓶颈上：失衡发生在注入侧 （挂接点抢纵环槽位），而 S16 管的是接收侧灌入量。 扣住占优 die 的授权只是让它手上没数据， 在环优先会立刻把空出的槽位交给下一个过路 flit，starved 的挂接点拿不到。 接收端驱动的拥塞控制能管“谁往瓶颈里灌多少”， 管不了“瓶颈处的仲裁不公”——单环研究里两者恰好重合，这里分离了。
  9. S17（挂接点转向仲裁）是本文提出的方案，但实测不成立——如实报告为负面结果。 它的思路是最对症的：既然根因是挂接点的转向 FIFO 被过路流量无限期压住， 就给这个 FIFO 一个有界耐心阈值， 连续被抢走槽位超过阈值后让一个过路 flit 在闩存里等一拍。 单个种子上看确实有效（Jain 0.93635 → 0.94495）。 但把阈值 1/2/8 各跑 3 个种子后，这个收益消失了： 唯一不比基线差的阈值是 8，平均 Jain 0.93643 → 0.94093 （差别在噪声量级），而最差 max/min 反而从 3.3898 恶化到 3.5088； 阈值 1 明显更差（Jain 0.91866、 max/min 4.7619）。 在 outstanding=32 上重复，结论相同。 先前的单种子结论是噪声。机理上的解释是：让位把槽位交给了转向 FIFO 的 队首，而队首未必属于那个被饿死的 core—— 局部仲裁公平并不等于端到端公平。
  10. 三个流控方案里只有 S1 站得住，而它又被一个免费的旋钮基本取代。 把四条结论并排看：路由决定织物能不能用（崩溃 vs 完成，各自最优并发度下也差 2.8 倍）； outstanding 免费地同时改善吞吐与公平； S1 有可靠但不大的增量，代价是一条专用广播总线； S16 与 S17 都无效。 最好的组合是 S1 + outstanding=32（平均 Jain 0.95465、最差 max/min 2.2727、 平均效率 95.6%）， 但它相对“只调 outstanding”（0.94847 / 2.2727）的增量很小。 工程结论：先调路由和 outstanding，再考虑是否值得为 S1 付一条总线。
  11. 所有运行时方案都没有达到验收线，真正的解法在布局层面。 验收线是 Jain ≥ 0.98、max/min ≤ 1.05； 维序路由下最好的运行时组合只到 Jain ≈ 0.95465、 max/min ≈ 2.2727。唯一达标的点是把 outstanding 压到 4（Jain 0.99489、 max/min 1.3158）， 但效率掉到 74%——那是用吞吐换公平，不是解决问题。 根本原因是成对相邻的挂接点布局把不对称写进了拓扑： 无论怎么仲裁，第二个挂接点永远在第一个的下游。 彻底的修法是改布局——把同一行间隙的两个挂接点分散到 纵环上相距较远的位置，或让同一间隙的两条横环反向行进， 使“第二个永远在下游”这个前提不再成立。 这样位置失衡会从结构上消失，不需要任何运行时机制。
一句话建议： 维序路由（必须，决定崩溃与否）+ outstanding≈32（免费， 吞吐与公平同时更优）+ 转向 FIFO 4~8 flit（够用，不必加深）。 这三项都不需要新增流控硬件。若仍需更公平，只有 S1 值得考虑 （代价是一条专用广播总线，增量有限）；S16 与 S17 实测无效。 若能改版图，优先分散成对挂接点，这比任何运行时机制都彻底。

2. 公平性指标：Jain 指数怎么算、怎么读

对 n 个 core 的带宽 x1…xn：

J(x) = ( Σxi )2 / ( n · Σxi2 )

它就是算术平均的平方除以平方平均，等价于 1 / (1 + CV2)，其中 CV 是变异系数。因此：

  • 取值范围 [1/n, 1]。全部相等时 J = 1； 只有一个 core 拿到全部带宽时 J = 1/n （本文 n = 60，下限 0.0167）。
  • 与量纲无关：所有带宽同乘一个常数，J 不变。 所以它衡量的是“分布形状”，不是绝对性能—— 一个吞吐极低但人人平等的方案 J 也等于 1。 这正是第 4 条结论里 outstanding=4 的陷阱， 也是本文每张表都把 Jain 与对下界效率并列的原因。
  • 可解释为“有效份额人数”：J ≈ k/n 意味着 效果相当于带宽被 k 个 core 平分、其余基本饿死。
  • 对少数离群点不敏感，这是它的弱点： 59 个 core 相等、1 个只有 1/10， J 仍然高达 0.9865。所以必须同时看 max/min（最快 ÷ 最慢，直接暴露最差个体）和 CoV（相对离散度）。本文三个指标一起给。

带宽的测量窗口。闭合批次里每个 core 最终都会发出同样多的 WriteData flit，跑完再数必然相等、毫无信息。因此统计窗口取 t_fair = 第一个 core 把自己的活干完的时刻； 在此之前全部 60 个 core 都在争抢同一批资源， 这段区间内的每核 flit 数才是真实份额。

5. 现象二：位置相关的每核写带宽失衡

纵轴是份额（每核带宽 ÷ 该方案自身均值）， 不是绝对带宽：不同方案的公平窗口 t_fair 长度不同， 绝对值不可横向比较，而份额正是 Jain 所度量的东西。 右图可以直接看出 S1（橙）把饿死的 die 1 从 0.63 抬到 0.81、 同时压低领先者，这就是它 Jain 更高的来源； S16（蓝）与 S0（红）几乎重合，说明它没有生效。

6.1 计划中的假设被否定

原假设：横环 t 在所有列切在同一纵向位置， 所以 top die t 的偏置是同相的， 带宽应当按 die 编号（vpos 1,2,8,9,15,16）单调排序。 同相这一点是对的，单调这一点是错的：

7. 三个流控方案

7.1 S1：按规格实现的拥塞等级 AIMD

四个部分按规格实现：检测（每站点每窗口统计上环失败与落环偏转， 等级 = min(7, 次数/8)）、传播（专用 3bit 广播总线，不占 NoC）、 反馈（每个源维护受控节点表，取其中最大等级）、 控制（终值 = level_of(自身失败 − 8×收到的最大净等级)， 对整数注入预算做 AIMD）。 唯一改动是受控节点表的构造：单环上是 (idx+dir) % n 走 hops 步， 这里改为沿路由的边表收集途经站点——机械替换，不是策略变化。

结果：Jain 0.93635 → 0.94549， max/min 3.5088 → 2.5641， makespan 1373 → 1359（略快）。 跨种子稳定，是三个方案里最可靠的。 局限在于 max 聚合让同一条纵环上的所有 core 收到相同的拥塞等级， 而真正要区别对待的是“同一行间隙里的第一个 vs 第二个”—— 所以它只能压掉一部分差距，不能对症。

7.2 S16：接收端驱动的授权（Homa 式）

WriteNoSnp 规定拿到 DBIDResp 之前不许发 WriteData， 所以完成端本来就握有“谁、何时可以把写数据放上织物”的权力， 基线只是一到就授权、把它浪费了。S16 不加报文、不加总线， 只改授权的时机与顺序（每完成端最多挂起 overcommit 个授权， 按已服务量最少优先）。在本拓扑上完成端（HA）还正好坐在瓶颈纵环上， 看起来是理想的控制点。

根本原因是控制点不在瓶颈上： 失衡发生在注入侧（挂接点抢纵环槽位）， S16 管的是接收侧的灌入量。 扣住占优 die 的授权只是让它手上没数据， 在环优先会立刻把空出的槽位交给下一个过路 flit， starved 的挂接点拿不到这个槽位。
这与单环研究的结论并不矛盾：单环上瓶颈就是完成端所在的那条环段， 控制灌入量等价于控制仲裁；这里两者分离了。

7.3 S17：挂接点转向仲裁（本文提出）

把上面全部结果综合成一个可落地的配置。 注意其中前三项都不是流控机制——它们是路由策略与两个已有参数的取值， 却贡献了绝大部分收益。

1（必须）维序路由：在目的列自己的 bridge 上跨 die，之后只走该列纵环，不走横环路由策略从拥塞崩溃（完成 5%）变为全部完成、效率 95%；各自最优并发度下吞吐 0.785 → 2.229 txn/cycle（2.8 倍）无（只改路由表/路由函数）

3（省成本）转向 FIFO 保持 4~8 flit，不必加深缓冲配置深度 4 与 64 的吞吐仅差 3.1%比原先设想的 64 flit 省 16 倍
4（可选）S1 拥塞等级 AIMD流控机制在 oc=32 基础上 Jain 0.94847 → 0.95465，最差 max/min 同为 2.2727专用 3bit 广播总线 + 每源受控节点表

若只能做一件事，做第 1 项； 若能做两件，做第 1、2 项——这两项加起来不需要任何新增硬件， 就把织物从崩溃状态带到效率 96.7%、 Jain 0.94847。S1 是唯一值得考虑的流控增量， 但要先确认那条广播总线的代价换得来那点增量。
