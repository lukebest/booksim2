3D 堆叠 NoC：按 top die 分组的写带宽

bottom die 横环 4 cycle / 纵环 6 cycle / 挂接点转向 5 cycle。 每 core outstanding = 413（最长写 RTT）， 每个 HA 跟踪表 16 项，超出回 RetryAck。 workload：60 个 AI core 均匀写 96 个 HA， 每 core 50 笔，共 3,000 笔。

结论

  1. outstanding 按最长写 RTT 取值是 413，不是一个拍脑袋的 600。 无拥塞的 WriteNoSnp 往返 = REQ 去程 + DBID 回程 + WriteData 去程 （4 flit 流水，最后一拍比第一拍晚 3 cycle）+ Comp 回程。 最坏一对 (core 4, HA 231) 的去程 58 cycle、回程 147 cycle，合计 413 cycle。额度从 REQ 上环一直占到 Comp 回来， 所以寄存器就写成这个数。本批次每 core 只有 50 笔， 峰值占用 50， 413 这个上限本身没有打满——它保证的是再长的往返也不会把 core 饿在等 Comp 上。
  2. HA 跟踪表满了就 retry，S0 / S1 都没有拥塞崩溃。 每个 HA 同时只能收 16 个请求；再来的 REQ 走 RetryAck → PCrdGrant → 重发 REQ，占真实 RSP/REQ 带宽。 S0 完成 3,000/3,000，makespan 2,327 cycle， RetryAck 1,350 次，有效并发是名义值的 80.6%； S1 同样排空（3,000/3,000，2,359 cycle， retry 1,343）。 两个方案都没有活锁、没有停在停滞检测器上。
  3. 按 top die 一组（10 个 AI core）看，写带宽在时间上是齐步走的， die 之间的完成量相同。 S0 组间完成量 max/min = 1.00， 组间 Jain 0.9897； S1 为 1.00 / 0.9872。 六个 die 最终写下的量一样，差异只在谁先跑完、过程中谁的瞬时带宽高一点。 下图是各 group 写带宽随时间的曲线。

　└ 分织物明细d2d 219 / h 871 / top 218 / v 1,308纵环 144 条、横环 48 条，横环少但只承担换列流量
