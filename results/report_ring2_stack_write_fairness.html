3D 堆叠 NoC 上的 per-core 写带宽公平性

拓扑：6 个 top die（每个 20 节点、双平面、 双向 full ring：10 个 AI core + 8 个 D2D bridge + 2 个非终端节点） + 48 条 D2D 链路 + 1 个 bottom die（96 个 HA，12 行 × 8 列； 6 条横向 + 8 条纵向单向 half ring）。 挂接点按 2 横 × 4 列 = 8 个一组挂到一个 top die； 每个 HA 与一个 D2D bridge 绑定。 workload：60 个 AI core 均匀写 96 个 HA， 每 core 50 笔 WriteNoSnp、每笔 4 个 WriteData flit，共 3,000 笔事务；每 core outstanding 上限 600。

结论

  1. 最重要的一条：outstanding = 600 会让这个织物直接拥塞崩溃， 而且只调节“怎么发”的流控一个也救不回来。 在规定的 outstanding=600 下，3,000 笔事务只完成 824 笔（27%）， 批次根本排不空；把 S1、S16、S17 分别加上去， 这四个方案全部崩溃（§7）—— 它们都只调节“怎么发”，没有一个限制“同时能有多少笔在飞”， 而后者才是崩溃的原因。 本文新增的 S18 正是补上这一点，它在同样的 outstanding=600 下 能把批次排空（见第 4 条）。 实测的边界很窄：跨 3 个种子， 到 outstanding = 5 为止每个种子都能排空， 从 6（3 个种子里有的排空、有的不排空） 起就变成时好时坏， 再往上（32、600）则每次都崩溃。 可用区间的上沿就在个位数， 而能不能排空在边沿上取决于运气，这本身就不能作为设计点。 换算下来，规定值比织物能承受的并发度高了约 120 倍—— 60 个 core × 600 = 36,000 笔并发写，而整个 bottom die 的纵向织物 只有 144 条有向链路。 多出来的在途报文不产生任何吞吐，只是变成互相阻塞的偏转流量： 偏转次数从 1,215 涨到 92,079。
  2. 换成以 top die 为单位统计，失衡比按 core 看严重一个量级。 一个 top die 的 10 个 core 共用一个环、一个挂接组、一套 8 个 bridge， 是真正不可再内部调度的单位。 在 outstanding=600 下，按 core 的 Jain 是 0.9094（看起来只是“略有不均”）， 但按 die 的完成量最快与最慢相差 88 倍： die 0、die 2、die 4 几乎完全被饿死，die 1、die 3、die 5 拿走几乎全部吞吐。 按 core 看不出来，是因为崩溃时同一个 die 内部的核同样惨 （最差 die 内部 Jain 仍有 0.8606）， 失衡整体落在 die 之间。 被饿死的正好是三个左半区 die—— 它们的远端流量在纵环上并入的位置处于下游， 而这个劣势对该 die 的全部 8 列同向， 所以整组 10 个 core 一起受损，不会在目的地之间被平均掉。 好消息是把并发度调对之后它完全消失： die 间完成量的 max/min 从 88 倍降到 1.00（六个 die 完成量完全相同）， 竞争窗口内的带宽 max/min 也从 1.66 降到 1.34。 所以 die 粒度的巨大失衡是拥塞崩溃的产物，不是拓扑的固有上限； 织物本身对六个 die 是对称的，只有过载时它才把对称性交给 “谁在纵环上游”这条规则。
  3. “配 600”和“真的能用 600”是两件事：完成方会把请求退回来。 HA 的请求跟踪表满了不能排队，CHI 要求它回 RetryAck 把请求退回发起方，再用 PCrdGrant 放行重发。 这条回路要真实带宽（2 个 RSP + 一次 REQ 重新过网）、 把请求打乱顺序，而且被挂起的事务仍然占着 outstanding 额度却毫无进展。 实测跟踪表深 2 时， 有效并发只剩名义值的 26.4% （1109.7 → 293.4 笔）， 平均挂起 1143.9 cycle。 反直觉的是这反而救了织物：深度 4 时批次 完整排空（Jain 0.9876）， 而跟踪表不限时只完成 824/3,000。 原因是 RetryAck 本质上是一种非自愿的准入控制， 把吃不下的请求挡在织物外面。 所以正确的结论不是“retry 有害”，而是 这个织物必须有准入控制；用一个明确的窗口去做， 可以省下那段挂起延迟（§5.5）。
  4. 一个静态 outstanding 伺候不了两个场景，所以动态流控是必要的而不是锦上添花。 outstanding 有两个方向相反的失效模式：太大则忙时崩溃， 太小则闲时盖不住往返时延。 实测这两个区间没有交集： 60 个 core 全在写时最好的静态值是 oc=5 （再往上崩溃），只有 10 个 core 在写时是 oc=32。 把所有场景一起看最差的那个， 最好的静态配置也只能拿到 50.7%。 本文因此给出 S18：发起方用自己测到的往返时延 （Comp 减去 REQ 发出时刻，本来就知道）当拥塞信号， 低于 rtt_min×(1+slack) 就涨窗口、越线就按比例回退、 收到 RetryAck 直接折半。 同一套参数不重配，窗口自己从 8.6（满载）走到 16.8（轻载）， 跨场景下限提高到 65.5%。 代价是每 core 三个寄存器，没有广播总线、 没有新报文类型、不改完成方（§7.5）。 要如实说明：在已知不变的负载上，调对的静态值仍然更好 （S18 只到最好静态值的 85.7%）， S18 换来的是不掉悬崖、也不在轻载白扔带宽。
  5. 如果负载形态是已知且固定的，最实用的一步就一句话：把 outstanding 从 600 改成 2，代价为零。 outstanding 上限本来就是一个已有的配置寄存器，改它不花任何硬件。 跨 3 个种子实测，outstanding=2 时： 3/3 个种子全部排空， 吞吐 0.881 txn/cycle （达理论下界 62.2%）， Jain 0.99866，最差 max/min 1.19—— 这是唯一严格满足 §2 那条公平线（Jain ≥ 0.99 且 max/min ≤ 1.5） 的可用配置。 代价要说清楚：稳定区内吞吐峰值在 outstanding=5（1.087 txn/cycle），2 只拿到它的 81.0%， 而峰值那一档公平性不达标 （Jain 0.97796、max/min 2.08）。 如果愿意让一点公平性换吞吐，outstanding=3 是更好的工程折中：Jain 0.99373 仍在 0.99 以上， 只是最差 max/min 1.52 略微越过 1.5 这条线， 换来 1.049 txn/cycle （峰值的 96.5%， 比 2 高 19.1%）。 两者都比规定的 600 好几个数量级。 但这条建议的前提是负载形态不变——上一条已经说明它不总成立， 所以它和 S18 是互补的两个答案，不是二选一的竞争关系。
  6. 路由在这个拓扑上不是可调项——目的地决定了一切。 每个 HA 与一个 D2D bridge 绑定：先确定去哪个 HA，就确定了走哪个 bridge， 两个 die 上的源和目的因此都被钉死，剩下的只是各 die 内部的最短路。 好消息是这个被规定的路由本身就是最好的： 它的下界 2,112 cycle， 比“无视绑定、全局自由最短路”的 3,360 cycle 还要好 1.59 倍， 因为自由最短路会诱导流量提前跨到 bottom die、 把稀缺的纵环当过路通道用（最忙纵向链路达到平均值的 4.54 倍，绑定路由只有 2.84 倍）。 换句话说，上一版报告里“换个路由就能提速”的那条结论在这个拓扑上不成立， 因为路由已经没有自由度了；能动的只有并发度。
  7. 横环不再是闲置的余量，它承担了一半的流量。 挂接组是 2 横 × 4 列，所以一个 top die 只直接覆盖 8 列中的 4 列； 去另外 4 列的写必须先在横环上走 4 跳换列。 每个 core 的目的地一半近一半远， 于是每笔事务平均在横环上产生 7.96 个 DAT flit·跳、 在纵环上 35.66 个。 横环只有 48 条有向链路（纵环 144 条）， 两者的峰值负载已是同一量级，但决定下界的仍然是纵环 （分织物下界：纵 1308 vs 横 871）。
  8. 残余失衡是结构性的，但它不是某个位置坐标的简单函数。 即使把并发度调到推荐值，位置性失衡依然存在： outstanding=5 下 Jain = 0.98276， max/min = 1.79， 每核带宽 0.06817 ~ 0.12173 flit/cycle， 而需求是完全对称的。 把带宽与各结构变量做秩相关，最强的是 “该 core 要并入的最忙那条纵环边的负载” （Spearman -0.703，方向正确但只是中等强度）， top die 编号只有 -0.3135， top 环上的位置只有 0.0322。 按 die 聚合后最好与最差相差 1.34 倍 （die 3 vs die 5）， 但存在反例：die 5 的纵环负载并非最高。 结论是：失衡可复现、可归因于“在环优先”下的并入竞争， 但无法约化成一个静态位置变量—— 这正是所有静态流控方案在这里收效有限的原因（§6、§7）。
  9. 一个免费的拓扑选择：同一行间隙里两条横环怎么分工，会改变越过上沿之后的劣化方式。 两种分配搬运的 flit·跳完全相同，解析下界一模一样 （都是 2,112 cycle）， 所以任何静态分析都区分不出来。 实测两者可靠上沿相同（都到 outstanding=5）， 差别在越过上沿之后的劣化方式和同并发度下的公平性： outstanding 6 时 split 还能排空 2/3 个种子、stack 只有 1/3，outstanding 7 时 split 还能排空 2/3 个种子、stack 只有 0/3，outstanding 8 时 split 还能排空 1/3 个种子、stack 只有 0/3； 而在推荐点 outstanding=2 上， split 的 Jain 是 0.99866、stack 是 0.99846。 原因是前者让两个 die 在同一列上落在不同的挂接点， 后者把它们挤到同一个挂接点上抢同一条出边。 收益不大但不花任何硬件，只是布线时的一个选择。
  10. 与上一版拓扑相反：转向 FIFO 深度这次是硬需求，而且它和并发度绑在一起。 计划把“横↔纵转向 FIFO 深 4 flit”列为风险项，这次它是对的： 深度 4 直接活锁 （只完成 168 笔，FIFO 全程被占满）。 原因是 2×4 分组让一半的写必须先走横环、再经转向进入纵环， 转向从上一版的“几乎不用”变成了关键路径。 好消息是这两个建议互相加强而不是互相拉扯： 跨 3 个种子实测， 在推荐并发度 2 下只需要 8 flit 深， 而所需深度随并发度陡升（outstanding 2 需要 8 flit；outstanding 3 需要 24 flit；outstanding 5 需要 64 flit）。 把并发度压下来同时省了面积。
  11. 三个原有流控方案的结论：S1 能跑但很贵，S16 打不到痛点， S17 收益不稳定。 在 outstanding=5 上跨 3 个种子： S1 Jain 均值 0.97796、 S16 0.97796、 S17 0.98176， 基线 S0 0.97796。 S16 的控制点在 HA 侧的授权发放，而瓶颈在纵环的并入仲裁上， 控制点和瓶颈不在一处，所以它的预算在正常负载下几乎不生效（§7.2）； S17 直接针对挂接点的转向仲裁，机理是对的， 按 core 看跨种子收益不稳定（§7.3）， 但换到 top die 粒度它的作用就清楚了： 在 outstanding=5 上它把 die 间 Jain 从 0.9903 提到 0.9936、 max/min 从 1.34 降到 1.28。 结论是：这三个方案都不如“把并发度控住”， 而控住并发度的两个办法（静态调对、或 S18 自己找）才是主线； S17 只在按 die 验收时值得叠加上去（§7.6）。

2　公平性怎么量：Jain 指数

对 n 个 core 的写带宽 x1…xn，Jain 指数定义为

J = (Σxi)² / (n · Σxi²)

取值范围 1/n ~ 1。全部相等时 J = 1； 只有 k 个 core 拿到带宽、其余为 0 时 J = k/n。 它的好处是与量纲和总量无关——把所有带宽同乘一个系数，J 不变， 所以可以直接比较不同吞吐下的公平性。

本文同时给出另外两个指标，因为 Jain 对少数极端值不够敏感： max/min（最快 core 与最慢 core 的带宽比，直观但只看两端）和 CoV（标准差／均值，看整体离散度）。 判定一次运行“公平”，本文用的线是 Jain ≥ 0.99 且 max/min ≤ 1.5。

5.5 名义 outstanding 不等于有效 outstanding

前面把 outstanding 当成一个纯粹的注入闸门，但完成方也有自己的额度。 CHI 里 HA 的请求跟踪表满了之后不能把请求排队： 它必须回一个 RetryAck 把请求退回发起方， 之后再用 PCrdGrant 发一个协议信用， 发起方收到信用才能重发这笔请求。 这条回路有三个后果，本节把它们分开测量：

  • 它要真实带宽：一次退回 = 1 个 RSP（RetryAck）+ 1 个 RSP （PCrdGrant）+ 一次 REQ 重新过网。
  • 它把请求打乱：被退回的那笔要排到后发的请求之后， 所以到达顺序不再是发出顺序。
  • 它吃掉 outstanding 额度而不产生进展：被挂起等信用的事务 仍然占着发起方的额度，却没有任何一个 flit 在路上。 所以名义并发（额度占用）大于有效并发（真正在推进的）， 而决定一个 core 能不能盖住往返时延的是后者。

7.5 S18：用往返时延自己找窗口（本文推荐的新方案）

既然要动态，就得先选一个反馈信号。RetryAck 看起来最现成， 但 §5.5 已经说明它来得太晚：这个织物的瓶颈在环上的并入仲裁， HA 的跟踪表在被压垮之前根本填不满， 所以只靠 RetryAck 的控制器会一路把窗口涨过悬崖。 真正能反映织物拥塞的免费信号是往返时延本身： 发起方本来就知道自己什么时候发出 REQ、什么时候收到 Comp。

S18 的控制环完全落在发起方本地：

  • 测：每笔写的往返时延；历史最小值 rtt_min 就是这个 core 自己的“无拥塞基线”， 它同时也定义了窗口的下限——要盖住往返，窗口不能比 带宽时延积更小。
  • 判：目标线 = rtt_min × (1 + slack)。 低于它说明织物还有余量，高于它说明这个 core 正在为自己制造排队。
  • 调：明显没拥塞时窗口几何增长（否则跨不过 5→32 这个量级差就已经过了这一相）， 接近目标线时改为加性小步；越线则按超出比例回退； 收到 RetryAck 直接折半。
实测：它自己走到了两个场景各自该在的位置。 同一套参数、没有为任何场景重新配过， S18（slack=2.0）的窗口在 all 6 dies 收敛到 1~18 （均值 8.6）， 在 1 die 收敛到 10~32 （均值 16.8）—— 方向和量级都对上了实测的最好静态值（5 与 32）。 跨场景的下限因此从最好静态值的 50.7% 提高到 65.5%。 测到的 rtt_min 约 78 cycle， 这也是“窗口不能太小”的定量依据。
代价，以及要如实说明的两点。 每个 core 三个寄存器（窗口、rtt_min、累加器） 外加每个在途表项一个时间戳——而重传超时本来就需要这个时间戳。 没有广播总线（对比 S1 的 66,528 bit 广播）、 没有新报文类型、不改完成方。 两点让步： 其一，在已知且不变的负载上，调对的静态值仍然更好—— all 6 dies 上 S18 只到最好静态值的 85.7%，因为它要花时间收敛， 而静态值一开始就在正确位置； 其二，各 core 依自己的 rtt_min 独立决策，窗口会有差异 （1~18）， 按 core 的 Jain 因此不如静态值 （0.8558 vs 0.99866）。 所以 S18 的价值不是峰值，而是不会掉下悬崖、 也不会在轻载时白扔一半带宽。

7.6 S19 = S18 + S17：两个问题分别用两个便宜的办法

S18 修的是“流量总量”，S17 修的是“谁先走”，两者互不干涉， 可以直接叠加。这也刚好对上 §6.2： die 粒度的失衡来自挂接点的并入优先级， 而这正是 S17 的作用点。

在按 top die 的粒度上，叠加是有意义的： S19 把 die 之间的 max/min 从 1.86 压到 1.48、die 间 Jain 从 0.9690 提到 0.9814，代价是完成时间长 4.5%（3,150 → 3,292 cycle）。 但要说清楚方向：这是把公平性从 die 内部挪到 die 之间，不是净增。最差 die 内部的 Jain 反而从 0.8533 掉到 0.7985——S17 让转向 FIFO 插队，受益的是被压住的那个挂接点整体，而同一个挂接点上先到的 core 因此更占优。所以只有当验收指标确实是按 die 时，这笔交换才划算。 如果最终的验收指标是按 top die 的均衡（本次的要求就是如此）， S19 是这份报告里代价最小、又同时覆盖两个失效模式的组合。
