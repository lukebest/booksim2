6×8 2D Mesh Allgather 三方案分析

Mesh 6×8（N=48），H=4 cy，V=6 cy，上/下 ramp 各 1 cy，下环带宽 ramp_bw ∈ {1, 2} flit/cy/节点，数据量 m ∈ {1..5} flit/节点。

物理模型与 Buffer 定义

  • 刚性 0-buffer 打包器（sched_zerobuf_compare.py）：每个源分配唯一注入偏移，使任意时刻每条有向链路 / 上环 / 下环最多被一个源占用——by construction 不需要 router 内部排队。
  • 事件驱动仿真（allgather_fast_sim.py）：允许 router 无限深队列，逐跳按最早可用周期转发；记录的 max_link_wait / max_ramp_wait 表示该热点资源为不丢包所需的最深排队（flit 数）。
  • 节点 SRAM 暂存（方案三独有）：行相结束后节点须本地攒够整行数据包 (MX−1)×m flit，再二次上环做列相——不是 router buffer，但是真实的本地存储与同步开销。
理论下界 T = max(弹出下界, 角节点下界, 延迟下界, 二分带宽下界)；6×8 在 m=1,ramp_bw=1 时 T=64 cy（角节点下界紧）。

方案一：Tree（multitree）+ 无阻塞·无冲突·router 无 buffer

每个源 s 沿本行向左右 fork，再沿每列向上下 fork（X→Y 维序双向树）。用刚性偏移打包使链路/ramp 全程无重叠。

  • m=1：严格 0-buffer 成立（multitree makespan 149@rb=1 / 96@rb=2，max_link_wait=max_ramp_wait=0）。
  • m≥2：高扇出结构下仅靠"每源一个全局偏移"已无法保证 0 重叠；事件驱动仿真显示下环口排队深度随 m 线性上升（rb=1 时 m=5 需 ramp 113 flit 深）。
  • 结论：tree 的"0 buffer"承诺是 m=1 专属；数据量增大后要么接受 router 排队，要么退回更慢但仍 0-buffer 的刚性调度。

方案二：ring_uni / ring_bi / hybrid_v_bi_B2

  • ring_uni：48 点 Hamilton 单向环，每跳 1 前驱 1 后继，几乎恒 0 buffer（link≤1, ramp=0），但 makespan 最差且几乎不随 ramp_bw 改善。
  • ring_bi：双向环，下环口 2 路汇合；link 侧仍近 0，ramp 侧随 m 增大出现排队（rb=1 最高 104 flit）；rb=2 时 ramp 排队被带宽翻倍压回 0。
  • hybrid_v_bi_B2：2 个 3 列纵带内局部环 + 逐行横向 fork；makespan 全场最优（m=1: 82 cy），但 buffer 诉求也最大（m=5@rb=1: link 56 / ramp 140 flit）。

规律：扇出/汇聚度越高 → makespan 越短、router 排队越深。buffer 需求 ring_uni < ring_bi < hybrid_v_bi_B2，与 makespan 优劣正好相反。

方案三：先 Row Allgather，后 Column Allgather

算法

  1. 行相：每行独立 allgather（6 节点），各节点获得整行 6m flit。
  2. 列相：每列独立 allgather，转发整行包（6m flit/次注入），完成后每节点持有 48m flit。

Buffer 诉求（两层）

  • 网络内（router/link）：严格 0 buffer，对任意 m 成立——1D fork 结构 + 刚性偏移在 6×1 / 1×8 虚拟网格上天然无重叠。
  • 节点 SRAM：(MX−1)×m = 5m flit/节点——第二阶段须等整行到齐、本地落地后再二次上环；tree/ring/hybrid 全程直通转发，无此暂存。
