同一块物理环、同一个流集、同一套冲突判据，只换 transport： 一边是 HPCA'22 的 E-tag/I-tag + 偏转机制（运行期分布式决策，只支持 unicast），一边是离线排好的静态拍图（编译期全局决策，环站可复制多播、 归约在 L1 做）。本报告只回答一件事 — 谁快、为什么快、在哪里反而慢。

一、两种机制到底差在哪

差别的根源只有一句：运行期决策必须为「猜错」准备缓冲，编译期决策不会猜错。 基线的桥 FIFO 与目的端重组缓冲都不是设计者的偏好，而是偏转与乱序的必然后果。

图：同一个环站，两种机制各要什么。红框是基线必须有、 拍图可以删掉的存储；绿虚线框是被删掉的部分。拍图把代价搬到了控制存储 （一张时隙表）和「故障后要重编译」上。
图：同一个冲突的两种处理。基线只能把 B 弹走绕圈 （多付跳数 + 乱序）；拍图在编译期就知道冲突，把 B 排到下一拍 （多付 1 拍，保序）。这就是 §5 里偏转率与重组缓冲峰值的来源。

二、主对比：六个集合通信的 makespan

三条腿同 m、同 σ、同 barrier 语义。先看 m=1（单 flit，多数场景由 时延地板决定），再看 m=13（多 flit，带宽与端口开始咬人）。

图：m=1 时六个集合通信的 makespan。三条腿各取自己最优的集合算法（算法与 transport 是正交的两根轴，用同一个算法压基线等于把基线做成稻草人）。绿柱才是同硬件口径的对比：`ring_base` 只支持 unicast，即 T0。紫柱是额外加了弧多播 + L1 归约之后的拍图，只有扇出型有紫柱 — 归约 / 收集 / 全交换无可复制，T1 与 T0 逐字段相同。下界为四个界（时延 / 弧负载 / 端口 / ramp）取最大。
图：m=13 时六个集合通信的 makespan。三条腿各取自己最优的集合算法（算法与 transport 是正交的两根轴，用同一个算法压基线等于把基线做成稻草人）。绿柱才是同硬件口径的对比：`ring_base` 只支持 unicast，即 T0。紫柱是额外加了弧多播 + L1 归约之后的拍图，只有扇出型有紫柱 — 归约 / 收集 / 全交换无可复制，T1 与 T0 逐字段相同。下界为四个界（时延 / 弧负载 / 端口 / ramp）取最大。
读图要点：m=1 时六个 collective 的最优拍图全部 恰好压在时延下界上（makespan == latency_lb），此时比的是「跨度 + barrier 数」， m=13 才切换到端口界与弧负载界。所以不能只用一个 m 下结论 —— 这与 §8 里「不能只用一个 R」是同一类错误。
顺带一个反直觉的读数：m=1 时弧多播买到的收益精确为 0 —— 广播 dim_2phase 的 T1 与 T0 都是 61 拍，一拍不差；此时最优方案反而是 flat（59 拍），因为单 flit 下拼的是最短临界路径，不是省带宽。 多播是带宽原语，不是时延原语。

三、谁赢谁输：分界线在哪里

图：m=13、同为 T0 能力时的「基线拍数 / 拍图拍数」。向右越长表示拍图赢得越多；右列附注同时给出加上 T1 多播硬件后的比值。分界线不是随机落下的：拍图赢：广播、全收集、全交换（流量本来就摊得开，拍图能把弧排满而基线要为偏转让路）；基线赢：归约、全归约（纯 fan-in，全部流量挤向同一个抽取点）；打平：收集。输的那两个原因见 §4 — 是下环端口的记账粒度，不是偏转有魔法。

四、为什么这几个模式上基线更快

m=13 下基线更快的是 归约、全归约，收集 只是打平。这与直觉相反，所以要把机理说清楚，而不是把它藏进平均值里：这几个模式都是多对一，所有流量挤向同一个 root 的抽取点，于是胜负完全由「一个抽取点每拍能吃几个 flit」决定。

图：把拍图模型的端口放宽，差距就合上了。拍图把一个抽取点整段（m·σ 拍）独占给一次传输；`ring_base` 按 L1 的 RAMP_BW 逐 flit 交错抽取。这是记账粒度的差异，不是机制优劣 — 端口翻倍后拍图反超或接近。两条 T1 方案没有红柱：`ring_base` 只支持 unicast，这两行没有可比的基线。

七、带宽利用率

图：两个利用率必须一起看。全局高而关键弧低 = 还能继续压；关键弧贴住自己的界 = 只能换流集。实测所有方案的「关键弧周期 / 关键弧下界」都是 1.00×，说明打包器在最忙那条弧上没有浪费 —— makespan 高于下界的部分来自相位 barrier 与端口，不是弧。

十、结论与口径

  1. 同能力（都只有 unicast）下，拍图赢在流量摊得开的模式，基线赢在纯 fan-in。m=13 拍图更快的是 全交换（1.83×）、全收集（1.20×）、广播（1.15×）；基线更快的只有 归约、全归约，收集 打平。 这条分界不是噪声，是下环端口记账粒度造成的：拍图把一个抽取点整段 独占，基线按 RAMP_BW 逐 flit 交错。端口放宽到 2 之后差距就 合上（见 §4），这才是同口径比较。
  2. 基线的代价不只在 makespan 上。全交换 m=13 偏转率 0.198 次/flit， 偏转既白吃弧周期又制造乱序，所以基线必须带桥 FIFO 与目的端重组缓冲； 拍图把这两块删成 0（转环驻留实测恒为 0、乱序恒为 0），代价搬到了控制存储 与「故障需重编译」上。
  3. 弧多播是唯一改变数量级的硬件增量，但只对 fan-out 生效。 广播上环 flit 从 611 降到 182、makespan 从 323 降到 95 拍；而归约、收集、 全交换收益精确为 0（fan-in 无可复制，全交换的 N(N−1) 条消息两两不同）， 验证套件对 17 个 (pattern, algo) 对断言 T1 与 T0 逐字段相同。
  4. 打到下界与抗故障/抗抖动是互斥的。旋转拍图 II_eff 精确等于弧负载 下界，代价是 27 个故障场景里 20 个无解、抖动吸收 0 拍。要鲁棒就得留松弛， 留了松弛就打不到下界 —— 选方案时这是一次显式取舍，不是可以同时拿到的两件事。
  5. 凡是「更快」的论断都必须带口径。σ=1 还是金属恒定 σ=2、T0 还是 T1 能力、1 个还是 2 个环站端口、R=1 还是 R=13 —— 换任一项都可能翻转结论， 本报告每张图都标了所用口径。
