1. 建模口径

  • 拓扑：8×6 mesh（82 无向链路）vs 折叠 2D torus（96 无向链路）。金属线恒定约束下 torus 每链路带宽减半（σ=2），对分带宽与 mesh 严格相等。
  • 金属线审计：mesh=82 · torus=96 · 比=1.171（torus 多约 17% 链路单位；折叠线长×2 的物理偏差见敏感度 delay×2）。
  • 类型：bufferable = 源端 grant 准入 + 路由器 FIFO/credit；bufferless = grant 逐拍预约路径、路由器零缓冲。
  • 仲裁器：CA 集中式 @ nid=28；DA 目的端分布式。
  • 同步：allgather/allreduce 默认 sync barrier（等齐 48 个 request 再统一 grant）；allgather 另做异步「每 grant = 一棵多播树」对照。
T = T_bound + R_rg + W_grant(ρ)  ;  R_rg = ℓ(src→arb) + T_sched + ℓ(arb→src)

2. 头条结论：控制平面才是 alltoall 的瓶颈

CA 下 alltoall 若对每条 (s,d) 流单独 request，共 48×47=2256 条控制消息挤入仲裁器 ≤4 个入端口。 解析收敛下界 ⌈2256/4⌉=564 cy；控制面 DES 实测 t_last_request=1136 cy （额外来自控制路径争用）。而 m=1 数据面下界仅 ~98 cy、FIFO 基线 makespan=192 cy。

两个有效缓解：

  1. Request 聚合：每源一条 request 覆盖全部目的 → 48 条，t_last_req 降到线延迟量级（~55），makespan 回到与 FIFO 同量级。
  2. DA 分布式：把收敛点打散到 48 个目的节点，消除单点 564 cy 税。

异步树避免了「等最远节点」的 barrier 税，但树间冲突使数据面可能更长；同步把冲突集中到统一排程，大 m 时摊薄 R_rg。

5. Mesh vs Torus

  • 对分带宽绑定的大消息 alltoall：二者数据下界相同（bisect 自检 ✓）。
  • 小消息 / 树形（broadcast、reduce）：torus 直径 55 vs mesh 94，DA bufferless broadcast m=1 为 58 vs mesh 97。
  • torus σ=2 的串行税在长消息聚合 alltoall 上可见（bufferable m=16 明显重于 mesh）。
  • bufferable torus 需 2 VC（dateline）→ 缓冲面积约翻倍；bufferless 靠时隙预约无需 VC。

8. 验证清单

  • 对分带宽相等：✓
  • torus σ=0.5 flit/cy：✓
  • Golden FIFO alltoall m=1 = 192（pg 参考 188）
  • bufferless 零驻留（68 组）：✓
  • 保序：✓
  • torus CDG 无环：✓
  • 控制收敛 alltoall 非聚合：t_last_req=1136 ≥ 500 ✓
  • 单播单调性 bufferable≲bufferless：⚠ （树 pattern 的 bufferable 快速路径会展开为单播、高估共享前缀负载——见 mono_note）

Tree patterns (allgather) use event-driven unicast expansion for bufferable, which over-counts shared multicast prefixes vs bufferless tree reservation — violations there are expected.

9. 已知局限

  • 金属线：按链路计数 torus/mesh≈1.17，非严格恒定；折叠线长×2 用 torus_delay_scale=2 对照。
  • 同 hop 延迟 7/9 对 torus 有利（白拿减半跳数）。
  • 多树 bufferable（allgather）用事件驱动单播展开近似，共享树边被重复计数。
  • reduce = gather + PE 本地归约（无网内算术），对齐 ADR-002/Arch-A2。
