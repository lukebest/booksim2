0 · 一句话结论与全文地图

iSLIP 原本是交叉开关上的算法：一次授权只占「一个输入 + 一个输出」， 所以「源不同、目的不同 ⇒ 无冲突」。把它搬到 8×6 的 2D mesh 和 2D 无缓冲环上， 这句判据两个方向都错——它既会放过真冲突（mesh 上 4.99%）， 又会挡住本可并发的传输（mesh 上 44.48%）。 本文因此为两种 fabric 各写一套冲突判据（D-M / D-R）， 在其上各写一个集中式 iSLIP 变种，并与各自的分布式基线在同一台稳态仿真器里对打。

四条最该记住的结论
  1. 判据必须分开写。mesh 的冲突是「路径上的有向链路 + 坡道口」， 环的冲突是「弧 + 上环口 + 下环口 + 转环同拍」。 只用「链路不相交」在环上会漏掉 1.08% 的真冲突， 并把可并发流数从 61.8 高估到 93.8。
  2. 决定成败的不是仲裁器有多聪明，而是冲突域记什么。 只记「资源在 t 之后空闲」（free_at）会产生前沿棘轮， data_span 是 mesh 3,797 / 环 1,957； 改成完整占用区间（interval）后是 mesh 150 / 环 120，相差 25.3× 与 16.3×。轮数一模一样。
  3. mesh 上集中化是为了省面积，环上集中化是为了可行。 mesh_base 用缓冲和信用换来能工作；无缓冲环没有缓冲可用， R4「转环必须同拍完成」是个需要未来信息的约束， 分布式环站只能靠偏转绕圈化解——这是 ring_base 掉吞吐的根因。
  4. 稳态里集中式两边都赢，但赢的理由不同。 λ* 从 mesh_base 0.40 → mesh_islip2d 0.48， ring_base 0.55 → ring_islip2d 0.75； mesh 那边同时省掉 48 个节点的输入缓冲 （面积净省 5.96×），环那边面积基本打平（1.05×）。

1 · 三个前提

下面所有讨论都建立在三条约定上。它们不是本文的结论， 而是「一次授权到底意味着什么」的定义；不先说清楚，后面的判据无从谈起。

1.1 授权制传输（authorized transfer）

源节点不能自行发包。它把「我还有哪些目的地要发」告诉集中仲裁器， 仲裁器回一个授权，授权里含一个明确的起始时刻 t₀。 源在 t₀ 那一拍准时注入，此后包沿既定路径无阻塞前进—— 因为仲裁器在发授权之前已经确认整条路径在需要的那些拍上都空着。 这与信用反压是两种世界观：信用制是「先发出去，遇堵再等」， 授权制是「先算好，发出去就不会堵」。

1.2 刚性零缓冲足迹

零缓冲意味着包在网络中途没有落脚点，于是足迹是刚性的： 授权时刻 t₀ 一旦定下，包在第 k 跳链路上占用的时间窗也就完全确定。 这让「有没有冲突」变成一个可以在授权前离线判定的问题—— 本文两套判据能存在，全靠这一点。

1.3 半开区间记法

全文统一：r 指一次被授权的传输，u 指它要独占的 任一资源（mesh 上是有向链路或坡道口，环上是环链路、上/下环口、转环点）。 传输 r 对资源 u 的占用区间是

occ_r(u) = [ t₀ + pre_r(u) , t₀ + pre_r(u) + dur(u) )

pre_r(u) 是从注入到该传输抵达 u 的累计线延迟， dur(u) 是占用拍数（单 flit 包 σ 拍，m flit 包 m·σ 拍）。 左闭右开：相邻两次传输可以在同一拍首尾相接而不算冲突， 判定统一写成 a1 < b2 且 b1 < a2。 8×6 的线延迟取 H=7（水平）与 V=9（垂直）， 坡道带宽 RAMP_BW=2。

2 · 为什么交叉开关的判据在两种 fabric 上都不成立

交叉开关里，一次传输只碰两个资源：输入端口和输出端口。 所以 iSLIP 只要保证「一个输入最多被选一次、一个输出最多被选一次」， 就自动无冲突。这个前提在网络里消失了：一次传输要碰一整条路径。

图 1 · D-M：mesh 上一次授权占用的是路径上的一串有向链路。ROMM 换路不改变跳数，所以换路也不会乱序。

于是原判据的两条腿同时断掉：

  • 不安全（假阴性）：src 和 dst 都不同的两条流， 路径完全可以压在同一条链路上。mesh 上抽样 38,334 对这样的流， 4.99% 实际冲突。 按老判据放行就是数据损坏。
  • 过严（假阳性）：同一个源的两条流，在交叉开关上必然冲突（共用输入端口）， 但在 mesh 上只要第一跳方向不同就毫不相干—— 实测 44.48% 的同源对其实可以并发。 把它们一律互斥掉，等于白扔掉这 44% 的机会。

并发度的量化：在真判据下贪心找极大无冲突集，mesh 平均能同时放 74.7 条流（最好 90 条）， 而交叉开关的置换上限只有 48 条。 也就是说，网络的并发度天生比交叉开关高， 用交叉开关的判据去管网络，既不安全又浪费。

3 · D-M：2D mesh 的冲突定义

一次授权在 mesh 上要独占的东西只有两类：路径上的每条有向链路， 以及两端的坡道口。三条子句合起来就是 D-M。

记号沿用 §1：r 表示一次被授权的传输 (VOQ(s,d), t₀, route, m, σ)，下面用 r₁ / r₂ 指两次不同的传输；e 表示一条有向链路（资源）； path(r) 是该传输经过的有向链路集合； pre_r(e) 是从 t₀ 到该传输抵达 e 的累计线延迟。

M1 · 有向链路互斥

∀ e ∈ path(r₁) ∩ path(r₂)：
[ t₀¹ + pre_r₁(e) , t₀¹ + pre_r₁(e) + m·σ ) ∩ [ t₀² + pre_r₂(e) , t₀² + pre_r₂(e) + m·σ ) = ∅

读作：两次传输若共用某条有向链路 e，它们在 e 上的占用区间必须不相交。 它禁止的是「同一拍占同一条 e」，而不是「共用 e」—— pre 逐链路不同，两次传输完全可以错时穿过同一条 e。 能否兑现这条自由度，就是 §6 两种冲突域的全部差别。

资源共 164 条有向链路：横向 (8−1)×6×2 = 84，纵向 (6−1)×8×2 = 80。 有向是关键——同一对相邻节点之间东行与西行是两个独立资源， 所以对向流互不干扰。这一条是主力约束，也是 all-to-all 下界的来源。

M2 · 坡道口（注入 / 弹出）互斥

每个节点的注入口和弹出口带宽 RAMP_BW=2，用容量为 2 的资源计。 它单独成条是因为链路互斥管不到它： 同一节点同时给两个不同方向发包，链路上毫无冲突，坡道口却可能超发。

M3 · 同 (src,dst) 序内串行化

同一对 (src,dst) 的多个包必须按序进网。这条不是资源约束而是语义约束， 它保证接收端不用重排。

为什么 all-to-all 的轮数下界是 96？ 把 8×6 网格从 x=3 与 x=4 之间切开，左半 24 个节点要给右半 24 个节点各发一个包， 共 24×24 = 576 个包，而跨过这道切口的同向链路只有 6 条（每行一条）。所以任何无冲突排程至少需要 576 / 6 = 96 个「链路-拍」，即轮数 ≥ 96。 实测 111 轮，比值 1.156—— 离信息论下界只差 15.6%。 这个割界同时说明：mesh 上再怎么优化仲裁，也逃不掉中切带宽。

ROMM 换路与保序

D-M 允许同一 (src,dst) 走不同路径：在 src-dst 构成的矩形内选一个中间点 w， 走「src→w 的 XY」+「w→dst 的 XY」。 关键性质是跳数恒为 dx+dy（图 1）——矩形内绕行不增加跳数， 所以所有候选路径的线延迟完全相同。这带来一个不太直观的好结论： 换路不会乱序，因此 M3 只需要管注入顺序，不需要禁止换路。 （实测 14,560 对 mesh 候选路径，延迟差为 0。）

4 · D-R：2D 无缓冲环的冲突定义

先说清拓扑，因为「2D 环」有歧义。这里是维度切片的： 同一行的 8 个节点共用一条物理双向行环（共 6 条）， 同一列的 6 个节点共用一条物理双向列环（共 8 条）。 每个节点既在一条行环上也在一条列环上，因此每个节点都是桥 （48 个桥）。 链路数：每条 k 节点的环有 k 条无向链路（含绕回）， 故 6×8 + 8×6 = 96 无向 = 192 有向。

图 2 · D-R：环上一次授权 = 行相弧 + 转环 + 列相弧。弧是环上连续一段，可绕回；转环没有缓冲，两相时刻被刚性绑定。

一次授权在环上要独占五类东西，对应 R1–R5：

子句资源为什么必须单列
R1 弧上链路互斥 行相弧与列相弧覆盖的每条有向环链路 主力约束。弧是环上连续一段，可以跨绕回链路。
R2 上环口（board） 源节点把包放上行环的插入点，board_ports 个 只看链路会漏检：两条流的弧完全不相交， 但若同一节点同拍上环，物理上做不到。 实测漏检里 79.5% 是 board-board 型。
R3 下环口（leave） 目的节点从列环取下包的抽取点，leave_ports 个 同理，占漏检的 11.6%。
R4 转环原子性 转环节点上「行环抽取点 + 列环插入点」同一拍 无缓冲 ⇒ 包不能在桥上等。这是全文最关键的一条， 也是集中化的唯一硬理由（见 §7）。
R5 同 (src,dst) 序内串行化 语义约束 与 M3 同源。最小弧集是延迟不变的，所以它同样不禁止换路。

空分复用：arc 还是 whole_ring

一个实现选择：环上同时能否有多个互不重叠的传输？

  • arc（默认）：以弧覆盖的链路为粒度互斥 ⇒ 一条环上可并行多段。 轮数下界 60，实测 69 轮。
  • whole_ring：整条环一次只服务一个传输（令牌环式）。 下界立刻涨到 192，实测 195 轮， makespan 5,280 vs 1,957， 代价 2.70×。
这 2.70× 是环设计里最贵的一个 二选一。它也解释了为什么 D-R 必须以「弧」而不是「环」为资源单位： 把互斥粒度做粗一点，省下的是仲裁器几百个比较器， 丢掉的是接近三倍的吞吐。

参照点 fixed·g=1：67 轮 / makespan 2,025 / 最热链路负载 60。 五子句逐条复核结果见 §12（R1–R5 全为 0 违例）。

5 · Part A：islip2d_mesh 算法逐步拆解

算法要解决的问题：48 个源、每源最多 47 条 VOQ， 每轮要挑出一批「彼此无冲突」的 VOQ 并给每条一个起始时刻， 使总时间尽可能短，同时不让任何 VOQ 被饿死。

5.1 与原版 iSLIP 的三处结构差异

交叉开关 iSLIP islip2d_mesh
请求单位每个 VOQ 一条请求线 整张位图一条消息：源 s 把 47 bit 残余 VOQ 一次带给仲裁器。 控制面消息恒为每轮 ≤ 2×48 条（request + grant），与积压无关。 实测每轮 83.9 条。
grant 指针挂在哪每个输出端口一个 每条有向链路一个：资源从「端口」变成「链路」， 指针数量随之从 48 变成 164。每个指针存一个源编号 （下一轮从第几号源开始轮转），⌈log₂48⌉ = 6 bit， 共 164 × 6 = 984 bit。
指针指向源而不是流：链路上的候选是 VOQ（ 2,256 条），若直接指向流需 ⌈log₂2,256⌉ = 12 bit（1,968 bit， 翻一倍）。两级分解让「选哪条流」= 链路选源 + 源选 dst， 两个 6 bit 字段各存在该存的地方。
什么叫「被选中」输出端口选中它 路径上每条链路都选中它（全路径一致 / unanimity）。 这是 AND 而不是 OR，所以一致率天然低： 实测只有 28.1%。
图 3 · iSLIP-2D 的一轮：两级指针（每资源 grant + 每源 accept）决定谁被授予，冲突域决定被授予者落在哪个 t0。

5.2 一轮的六个步骤

# ---- 一轮 iSLIP-2D（mesh）。所有源同步进行 ----
# 状态：R[s] = 源 s 的残余 VOQ 位图（47 bit，1 = 还有包没被授权）
#       g[e] = 每条有向链路的 grant 指针（指向 48 个源之一）
#       a[s] = 每个源的 accept 指针（指向 48 个 dst 之一）
#       D    = 冲突域（free_at 或 interval），记已被占用的资源时间

# ① REQUEST：一条消息带出整张位图，不是每个 VOQ 一条消息
for s in sources:
    req[s] = R[s]                      # 1 条消息 / 源 / 轮

# ② GRANT：每条链路独立地沿自己的指针做一次 RR
for e in directed_links:
    cand = [ (s,d) for s in sources for d in bits(req[s])
             if e in path(s,d) ]       # 谁的路径压在我身上
    grant[e] = rr_pick(cand, start=g[e])

# ③ ACCEPT：一条 VOQ 只有在它路径上"每一条"链路都选中它时才算候选
unanimous = [ (s,d) for (s,d) in requested
              if all( grant[e] == (s,d) for e in path(s,d) ) ]
for s in sources:
    take = rr_take(unanimous[s], start=a[s], k=grants_per_src)
    for (s,d) in take:
        g[e] = advance(g[e]) for e in path(s,d)   # 指针只在成交后前进
        a[s] = advance(a[s])

# ④ FILL：一致相通常只填掉一小部分容量，按静态序贪心补齐
for (s,d) in remaining_requests sorted by fill_order:
    if compatible_with(selected, (s,d)):   # 逐资源查 D-M
        selected.append((s,d))

# ⑤ COMMIT：为每个被选中的 VOQ 求最早可行 t0，然后占区间
for (s,d) in selected:
    t0 = D.earliest( resources_of(s,d), lower=now + T_rtt )
    D.occupy( resources_of(s,d), t0 )
    grant_message(s, d, t0)            # 授权里带明确起始时刻
    R[s].clear_bit(d)                  # 只有成交才清位

# ⑥ 未成交的位原样留在 R[s]，下一轮继续带出 ⇒ 控制面消息数与积压无关

为什么需要第 ④ 步「补齐」

这是把 iSLIP 搬到网络上最容易被忽略的一点。 交叉开关上一致相能填满整个置换（每个输出都能成交一个）， 但在 mesh 上一条 VOQ 要跨 dx+dy 条链路， 只要有一条链路把 grant 给了别人，这条 VOQ 就落空。 一致率只有 28.1%，也就是说 光靠 iSLIP 的两级指针，每轮容量的绝大部分是空着的。 补齐步骤按静态序（默认跳数降序）把剩余请求逐条试塞进去， 只要过 D-M 就收。指针只在一致相里推进， 所以补齐不破坏 iSLIP 的无饿死性质。

一个反直觉的实测结果：把一致相整个关掉（iters=0， 只留补齐）反而轮数最少——97 轮 vs 保留一致相的 110 轮，即一致相带来约 13% 的额外轮数。 原因是一致相会「占着容量却填不满」： 它先把一批链路的 grant 指针分配给一组注定凑不齐全路径的 VOQ， 补齐步骤反而少了自由度。 一致相真正的价值在公平性（指针保证无饿死）而不是效率； 如果只看 makespan，应该把它当成一层薄薄的反饿死保险， 而不是主要的匹配机制。

6 · 冲突域：free_at 与 interval

仲裁器要回答的最后一个问题是「这条被选中的 VOQ 最早能从哪一拍开始」。 答案取决于冲突域记了什么，而这是全文影响最大的单个实现选择—— 比换路、比 grants_per_src、比端口数都大一个数量级。

图 4 · 冲突域：同一条链路的时间轴。两者的仲裁决策完全相同，差别只在被授予者落到哪个 t₀——所以这不是一项精细化，而是稳态下能否工作的分界。

两种记法

  • free_at：每个资源只记一个时间戳「我在 t 之后空闲」。 查询 O(1)，硬件只要一个寄存器（mesh 共 3,120 bit）。
  • interval：每个资源记一段滑动窗口内的完整占用位向量。 可以回填空洞，代价是位向量存储（mesh 共 99,840 bit，约 32×）。
前沿棘轮（frontier ratchet）：free_at 的问题不是「不够精细」， 而是会自我放大。提交一条流时，它必须把路径上每一个资源的前沿 都推到「整条路径都能开始」的那个最大值—— 包括那些其实很空闲的资源。于是一条拥塞链路把自己的滞后 输出给了它接触的所有链路，再逐跳向外扩散。 批量口径下 data_span 从 150 恶化到 3,797 （25.3×），环上从 120 到 1,957 （16.3×）， 而两者轮数完全相同——仲裁决策一模一样， 差别纯粹来自「落在哪个 t₀」。

所以 interval 不是一个「可选优化」， 而是集中式排程能否兑现「错时穿过同一链路」这个卖点的前提。 不加它，集中式的吞吐会掉到分布式基线以下。

实现陷阱：多服务器资源（如 RAMP_BW=2 的坡道口、 board_ports>1 的上环口）不能用「按拍取或」来判可用。 必须检查存在某一个服务器在整段 dur 上都空闲—— 否则会出现「第 0 拍服务器 A 空、第 1 拍服务器 B 空」被误判为可用， 而单个传输无法在两个服务器之间跳。这个 bug 曾被容量断言抓到。

7.2 R4：为什么这件事分布式做不了

图 5 · R4 转环原子性：无缓冲 2D 环之所以需要集中式上/下环仲裁。

R4 要求转环在同一拍完成：包从行环被抽出的那一拍， 必须同时被插入列环。零缓冲的定义就是桥上没有落脚点。 集中仲裁器能满足它，因为它同时掌握两条环的未来占用， 可以挑一个两边都空的拍——实测 max_turn_residency = 0， R4 违例 0。

分布式环站做不到，因为它只有本地视野：包已经在行环上跑了， 到桥才发现列环那一拍被占。此时它只有三条路： 加缓冲（就不再是无缓冲网络了）、 偏转（绕整环一圈再试，吃掉一整圈时隙）、 或者活锁。ring_base 选的是前两者的组合。

这就是「集中化不是为了更快，而是为了可行」的完整含义。 在 mesh 上，分布式方案（信用反压）是可行的，集中化换来的是省掉缓冲； 在无缓冲环上，R4 是一个需要未来信息的约束， 分布式方案只能用偏转把它化解掉，代价直接记在带宽和乱序上： λ* 从 ring_base 0.55 提到 ring_islip2d 0.75（1.36×）。

8 · 两个分布式基线

8.1 mesh_base：有缓冲 + 信用反压

教科书式的分组交换 mesh：每输入端口一组 VC 缓冲， 信用（credit）保证不会发到满缓冲上，交换分配用输入队列 iSLIP。 它是分布式方案在 mesh 上可行的证明， 代价是每节点的缓冲——614,400 bit 输入缓冲 + 1,440 bit 信用计数器 + 720 bit 分配指针， 合计 616,560 bit。

缓冲深度是它的命门：浅缓冲下信用反压把拥塞逐跳往回传， λ* 明显下降。这也是集中化的卖点所在——授权制根本不需要这些缓冲， 因为包发出去就不会堵。

8.2 ring_base：E-tag / I-tag + 偏转

按 HPCA'22《Application Defined On-chip Networks for Heterogeneous Chiplets》与 HiRD 谱系重建的反应式基线。 它不做任何事前无冲突保证，而是逐拍化解：

图 6 · 基线 ring_base（E-tag / I-tag + 偏转）：用事中化解代替事前排程，代价是带宽、乱序与每个桥的缓冲。
  • 环内优先：已在环上的 flit 永不停留（实测零违例）， 新注入只能抢空时隙。
  • I-tag：源节点长期抢不到空时隙时，为它预留一个时隙 ⇒ 注入保证。
  • E-tag：flit 长期转不过去时，为它预留 transfer FIFO 槽 ⇒ 转移保证。
  • 偏转：transfer FIFO 满时，flit 绕整环一圈再试。
  • Swap Rule：两侧互相转向时直接交换，绕过 FIFO。
  • 重组缓冲：偏转和交换都会乱序，目的端必须重排。

三个与预期不同的实测结果（都已写进验证清单）：
  1. 固定维序（RC）下 Swap Rule 从不触发—— 它需要两侧同时互相转向，而固定维序不产生这种模式。 要让它动起来必须允许双向转弯（dim_order=mixed）。
  2. 关掉 Swap Rule 也不会死锁：偏转通道永远可用， 包总能绕回来再试。原文的死锁场景需要更紧的时隙约束。
  3. 真正的失效模式是活锁而不是死锁：包一直在绕圈但不推进。 I-tag / E-tag 的预留机制正是为此存在，它们把「不推进」变成有界等待。

分布式硬件账（198,528 bit 合计）： transfer FIFO 49,152 · 预留 Tx 12,288 · 弹出队列 24,576 · 重组缓冲 98,304 · 饿死计数器 1,728 · I/E-tag 状态 192 · Swap 旁路 MUX 12,288。 其中重组缓冲（49.5%） 纯粹是偏转导致乱序的代价，集中式方案不需要它。

10 · 保序、流水与 RTT 敏感度

10.1 为什么换路不会乱序

直觉上「多路径 ⇒ 乱序 ⇒ 需要重组缓冲」。 在这两种 fabric 上，只要限定在最小路径集内，这个直觉是错的：

  • mesh ROMM：矩形内任意中间点给出的两段 XY，跳数恒为 dx+dy， 线延迟完全相同。实测 14,560 对候选路径，延迟差 0。
  • 环最小弧集：RC（先行后列）与 CR（先列后行）的最小路径 跳数与线延迟也相同。实测 2,256 对，延迟差 0。

所以 M3 / R5 只需要保证同 (src,dst) 的注入顺序， 不必把路径钉死。这直接省掉了目的端的重组缓冲—— 对比 ring_base 必须为偏转付出的 重组缓冲，这是集中式的一项实打实的收益。

反面情形：如果放开到非最小环路径（允许绕远）， 延迟不变性立刻破裂——93.6% 的 (src,dst) 对出现延迟差， 最大差 78 拍。所以「换路自由」必须限定在最小路径集内， 否则就要重新引入重组缓冲。

10.2 流水与 RTT 临界点

批量口径下引入 pipeline_depth：控制面算第 k+1 轮的同时， 数据面在跑第 k 轮。衡量指标是 convoy_ratio = convoy_span / data_span—— 硬 barrier（每轮等齐）相对流水的倍数，越大说明流水收益越大， 跌到 1 说明流水已被 RTT 完全吃掉。

11 · 面积与调度时间

「集中化消掉了什么」需要面积数字而不只是定性论断。 下表把分布式侧被删掉的存储与集中侧新增的仲裁器状态放在同一口径 （bit 等效）下结算。

方向删掉的分布式存储新增的仲裁器状态净账关键路径
mesh：集中化前后616,560 bit
输入缓冲 + 信用 + 分配指针		103,532 bit
位图 + 两级指针 + interval 表		5.96× 净省13 级 / T_sched=220 拍
环：集中化前后198,528 bit
FIFO + 预留 Tx + 重组缓冲		189,528 bit
弧表 + 端口计数器 + interval 表		1.05×（基本打平）15 级 / T_sched=138 拍
  • mesh 上集中化是净赚的：5.96× 净省， 因为输入缓冲（614,400 bit）本身就是 mesh_base 面积的绝大部分， 而授权制根本不需要它。
  • 环上集中化面积基本打平（1.05×）： 删掉的 FIFO 和重组缓冲，差不多正好被 interval 表吃回去。 所以环上集中化的理由不能是省面积，只能是 §7.2 的可行性 与 §9 的吞吐。
  • interval 表是最贵的单项：mesh 上 99,840 bit， 占仲裁器的 96.4%。 但 §6 已经说明它换来 4.6–4.7× 的接受吞吐—— 这是全设计里性价比最高的一笔存储。
  • T_sched 会翻倍（free_at 110 → interval 220 拍）， 门级深度从 9 升到 13 级。若时序吃不下， 应该做的是把仲裁流水切深（§10.2），而不是退回 free_at。

12.2 已知局限

  • E-tag/I-tag 是重建口径：HPCA'22 原文在付费墙后， 本文按论文描述与 HiRD 谱系重建了机制骨架 （环内优先、注入/转移保证、偏转、Swap Rule、死锁检测）。 定量结果应视为「这一类反应式策略」的代表，而非对原设计的复刻。
  • 与 HiRD 的结构差异：HiRD 是局部环 + 全局环的层次结构， 只有少数节点是桥；本文是维度切片，每个节点都是桥， 所以桥资源竞争更激烈、偏转代价更高。
  • 死锁未能复现：见 §8.2。在本文的时隙模型下偏转通道永远可用， 需要更紧的时隙约束（slot_ring）才能构造出死锁。
  • interval 窗口有限：滑动窗口 + rebase 实现， 窗口外的空洞看不见。窗口取 128 拍时已经拿到绝大部分收益， 但它不是「完整区间表」的等价物。
  • 未做 BookSim 交叉验证：本轮按要求跳过。 准备工作已就绪（utils/xval_booksim_8x6.py 能生成 8×6 anynet 拓扑与配置并解析输出）， 但当前环境缺 flex/bison 且无法取得 sudo，故 mesh_base 的延迟-吞吐曲线 仅有自洽性验证（解析锚点、缓冲深度单调性）而无第三方对照。
