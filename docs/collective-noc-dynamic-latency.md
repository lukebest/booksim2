# 集合通信 NoC 的动态时延：来源分解与确定性低时延的实现路径

> 用图论 + 排队论 + 系统观，回答四个问题：
> 1. 集合通信在基线分组交换 NoC 上的动态时延从哪来？多少归因于集合通信 pattern，多少受限于 NoC 本身属性？
> 2. 源端注入控制 + 分组交换 buffer 解冲突，能走多远？
> 3. 源端注入控制 + router calendar 排图，能走多远？
> 4. 考虑芯片实现面积，确定性低时延集合通信的最佳方案是什么？
>
> 本文所有数字来自本仓库基于 BookSim2 扩展的仿真与解析模型（`results/` 与 `docs/` 下的实验产物），
> 主要实验设置有三套，引用时会注明：
> **①** 6×8 mesh（48 节点，H=7/V=9 cycle 链路，ramp 1 cycle、`ramp_bw=1`，flit=64 B，2 GHz）；
> **②** 8×6 broadcast-tree 面积/微架构 DSE（H=7/V=9）；
> **③** 4×4~64×64 规模扫描与 16×16 深挖（H=4/V=6）。

---

## 0. 一页结论

- **基线分组交换 NoC 上，集合通信的时延中"物理必然"的部分只占约 1%。** 6×8、m=4 的 allgather，理论下界 188 cycles，FIFO 分组交换实测 15,880 cycles——**98.8% 是动态排队时延**，且不可控地随负载放大（`results/nc_mesh_analysis.json`）。
- 这 98.8% 的动态部分是 **pattern 与 NoC 属性的乘积**：pattern 提供了最坏形态的到达过程（N 个源同步突发、树形汇聚扇入），NoC 提供了放大器（无准入控制的 FIFO 仲裁、HOL 阻塞、共享缓冲的类间干扰、credit RTT）。单独归因给任何一方都不成立，但**消除它只需要控制一方**——到达过程。
- **源端注入控制 + buffer 解冲突**：能把 makespan 打到理论下界（8×6 广播树 96 cycles = LB，只需每输入 2 flit 突发缓冲；16×16 allgather 263 vs 下界 255，+3%），时延是"确定的重放"——但确定性是**封闭世界假设下的**，且到达下界的代价是缓冲面积（16×16 时单点峰值缓冲 118 flit；8×6 全下界配置路由器面积 1.356×基线，+32%）。
- **源端注入控制 + router calendar 排图（零缓冲）**：集合通信时延 **精确钉在排图 makespan 上、路由器内排队为 0**，对背景流量注入率 λ=0.02~0.3 完全免疫。代价是刚性排图的展宽：16×16 为下界的 1.31×，随规模增大逐步收敛（32×32 为 1.16×，64×64 配合每输入 1~3 flit 对齐缓冲可到 1.08×）。calendar 表本身很便宜（稀疏化后 5,888 bit/router，≈0.9% 路由器面积）。
- **面积最优的确定性方案不是"加东西"，而是"搬走缓冲"**：把确定性从路由器缓冲搬到离线排图 + 源端注入，集合通信路径零缓冲直通，只给背景流量留一个小共享池。最终架构（Arch-A5）面积是基线输入队列 XY 路由器的 **0.746×（省 25.4%）**，同时集合通信时延严格可复现、背景单播有 ~160 cycles 的进度上界。

## 1. 模型：把问题放进三套语言里

### 1.1 图论语言：集合通信 = 逻辑 DAG 在 mesh 上的嵌入

一次集合通信是一个逻辑数据流 DAG（broadcast/reduce 是树，allgather 可以是多树叠加或 Hamilton 环，alltoall 是完全二部流量），要嵌入到物理图 \(G=(V,E)\)（2D mesh，每条有向链路每周期 1 flit）。嵌入质量由三个经典指标刻画：

- **dilation（展宽）**：逻辑边映射到物理路径的拉伸。②号实验中，最短路轴向树 dilation=96 cycles（恰为图直径加权距离），列梳树 114，Hamilton 双树 210——树选错了，起跑线就落后 2 倍。
- **congestion（拥挤度）**：单条物理链路被多少逻辑边复用。同一组方案里 link_reuse 从 24 到 42 不等，它直接给出流水化时的发起间隔（II）下界。
- **fan-in（扇入）**：gather/reduce 树的内部节点入度。①号实验里 gather 的热链路（root 入边）要承载 144 flit（47 源 × m=4 的绝大部分），这是 pattern 自带的结构性热点。

嵌入决定了**静态下界**。本仓库对 allgather 推了五族下界并取 max（`results/allgather_lb.json`）：

| 下界 | 表达式（直觉） | 属于 pattern 还是 NoC？ |
|---|---|---|
| eject（弹出） | \(\lceil (N-1)m/\text{ramp\_bw} \rceil\)，每节点必须收下所有人的数据 | 流量总量是 pattern；除数 ramp_bw 是 NoC |
| corner（角节点割） | 角节点只有 2 条入链路 | 拓扑（NoC） |
| latency（直径） | 最远点对最短路时延 | 拓扑 + 链路延迟（NoC） |
| bisection（二分） | 跨切割流量 / 切割链路数 | pattern 的跨界流量 × NoC 的切割带宽 |
| release（释放序） | 源端串行注入的最早完成时间 | pattern × 注入带宽 |

规律很清晰：**小规模、小消息时 latency（NoC 的直径）绑死**（4×4 时 T=50 全由直径决定）；**规模或消息一大，eject/release（pattern 的流量 × NoC 的 ramp 带宽）绑死**（16×16、m=1 时 T=281 由 release 决定，eject=255 紧随其后；64×64 时 T=4121 完全是带宽界）。这回答了问题一的"静态半边"：

> **下界本身就是 pattern 与 NoC 属性的乘积——pattern 决定必须搬运多少数据、在哪里汇聚；NoC 属性（ramp 带宽、链路延迟、切割宽度）决定哪条下界收紧。** 两者在下界层面就不可分离，可分离的是下界之上的"超额时延"。

### 1.2 排队论语言：动态时延 = 到达过程 × 服务纪律的失配

下界之上的部分才是"动态时延"。集合通信的到达过程有两个恶劣特征：

1. **同步突发**：barrier 之后 N 个源在同一周期注入，等效于批到达（batch arrival），瞬时 ρ≫1；
2. **结构化汇聚**：树的扇入让多个流在确定的节点上必然相遇，不是随机碰撞，是 pattern 保证的碰撞。

基线分组交换路由器用 FIFO/VC 仲裁来消化这种到达，属于"用缓冲和排队换取对到达过程零假设"的服务纪律。对这种输入，排队论的预言是超线性爆炸——实测正是如此（①号，network-calculus + 仿真，`results/nc_mesh_analysis.json`，m=4，与泊松背景流共存）：

| 服务纪律 | allgather 集合时延（cycles） | 集合流缓冲占用（flit） | 背景流时延 | 说明 |
|---|---:|---:|---:|---|
| 理论下界 | **188** | — | — | eject 界 |
| **FIFO（基线分组交换）** | **15,880**（84× LB） | 无界（实测端口峰值 510+） | 3,009 | 类间无隔离，互相放大 |
| PRIO_DYN（集合流高优先级） | 1,800 | 168 | 2,066 | 优先级救不了汇聚突发 |
| TDM（硬时分 1/16） | 233 | 0 | **21,988** | 集合流好了，背景流饿死 |
| CAL_SHAPED（calendar+整形） | 210 | **0** | 4,028 | 见第 4 节 |
| **CAL_SOFT（calendar+软优先）** | **188 = LB** | **0** | 1,833 | 见第 4、5 节 |

FIFO 行的病理学：随着集合通信周期（发起频率）加快，coll_delay 从 17,461 恶化到 1,920,620 cycles——系统趋于不稳定，缓冲需求同步爆炸（端口缓冲从 583 涨到 214,762 flit 当量）。**这不是"再加点 buffer"能修的：排队时延的根源是到达过程失控，缓冲只是把等待具象化为面积。**

### 1.3 系统观语言：确定性可以放在三个位置

端到端路径 = 源端注入 → 网内传输/仲裁 → 目的端弹出。确定性（时延可预测、可复现）可以在三处建立：

- **源端**：控制注入时刻与速率（到达曲线整形，网络演算里的 \(\sigma,\rho\) leaky bucket，极限是逐周期指定注入 offset）；
- **网内**：要么用缓冲吸收残余冲突（elastic，事件触发），要么用 calendar 逐槽指定转发（time-triggered，时间触发）；
- **目的端**：eject/ramp 带宽是多数集合通信的真瓶颈（上表 dom=eject），这里没有魔法，只有带宽。

后面第 3、4 节比较的两条路线，本质是**网内那一段用什么机制兑现源端承诺**：buffer 是"乐观 + 弹性兜底"，calendar 是"悲观 + 逐槽契约"。

## 2. 问题一：基线分组交换 NoC 的动态时延，账算给谁？

把 1.1 和 1.2 合起来，可以给出一张完整的分解账单（以 ①号 6×8、m=4 allgather 为标尺）：

```
端到端时延 15,880 cycles (FIFO 基线)
├── 静态必然部分：188 cycles（1.2%）
│   ├── pattern 贡献：每节点必须吸收 (N-1)·m = 188 flit 的流量总量、
│   │                树/环的汇聚结构（热链路 168 flit）
│   └── NoC 属性贡献：ramp_bw=1 使 eject 界收紧为 188；
│                    H=7/V=9 的直径 94 在此规模下不绑定
└── 动态超额部分：15,692 cycles（98.8%）
    ├── 同类冲突排队：N 源同步突发 × 树扇入 → 确定会发生的碰撞，
    │                交给 FIFO 仲裁后变成随机串行化（pattern 提供火药）
    ├── 类间干扰：集合流与背景单播共享 FIFO/VC，互为长尾
    │            （NoC 无隔离机制提供引信）
    └── 协议性停顿：credit RTT（V 向 ≈20 cycles）> 浅缓冲深度时的气泡、
                   HOL 阻塞（NoC 微架构放大）
```

三个层次的归因结论：

1. **静态下界层（~1%）**：pattern 与 NoC 属性以乘积形式共同决定，问"各占多少"没有意义；有意义的问法是"哪条下界绑定"——小网络绑在 NoC 的直径上，大网络绑在 pattern 流量 ÷ NoC ramp 带宽上。
2. **动态超额层（~99%）**：形态上是 pattern 的错（同步突发 + 结构性汇聚是最坏到达过程），机制上是 NoC 的错（FIFO/VC 对到达过程零假设，用无差别排队应对确定性碰撞）。**但工程归因应该看"最小干预点"：pattern 是应用语义，改不了；到达时刻和网内仲裁是可以设计的。所以动态时延应记在"NoC 没有利用 pattern 的先验知识"这笔账上。** 集合通信恰恰是全网通信中先验知识最完整的一类——参与者、数据量、通信结构全部编译期已知——基线分组交换把这些信息全部扔掉了。
3. **一个佐证**：broadcast 的 pattern 几乎无冲突（m=4 时最大链路负载仅 4 flit），但 FIFO 基线下时延仍达 12,077 cycles（LB=94 的 128 倍）——这部分几乎纯粹是类间干扰和仲裁噪声，即**纯 NoC 属性造成的动态时延**。对比 gather（热链路 144 flit，结构性汇聚重），FIFO 下 2,486 cycles（LB 的 13 倍）。可见"pattern 温和"完全不能保证低时延，**共享 + 无准入的 NoC 本身就是动态时延的充分条件**。

## 3. 问题二：源端注入控制 + 分组交换 buffer 解冲突，能达到多少？

这条路线保留分组交换路由器，但离线计算每个源的**注入偏移（inject offset）**，把可预见的碰撞在时间上错开；错不开的残余冲突靠路由器缓冲吸收。排队论视角：到达曲线被整形成与服务能力匹配，缓冲只处理有界的相位失配，backlog 从"无界随机变量"变成"有界确定值"。

### 3.1 性能：可以打到下界

- **广播树（②号 8×6，LB=96）**：`results/burst_sweep_8x6.json` 的扫描给出干净的剂量-响应曲线——B=0（零缓冲）110 cycles，B=1 → 98，**B=2 → 96 = LB**。且达标还需最短路轴向树 + crossbar 输出容量 8（out_cap=6 时 100，=5 时 107）。最便宜的达界配置就是 `{buffer: 2, out_cap: 8}`：**缓冲的作用不是"抗拥塞"，而是给转角处 1–2 cycle 的相位对齐**。
- **allgather（③号 16×16，eject 界 255）**：`results/buffer_pareto_16x16.json`，multitree + 流水化缓冲达到 pipe=263（**+3.1%**），makespan 完全由 eject 界主导（dom=eject）。规模扫描（`allgather_scale_sweep.json`）显示比值稳定在 1.00–1.10，且越大越贴近下界（32×32 为 1.01×）——因为大网络是带宽绑定的，时间上错峰的空间充裕。
- **流水化多轮（②号，R=5 轮连发）**：`results/multiflit_area_makespan.json`，axis+CCW 在 W=4/B=11 时 t1=96 = LB 且 **II=47 = 发起间隔下界**（max(link_reuse, ⌈(N-1)/E⌉)）——buffer 同时买到了填充时延和吞吐两个下界。

### 3.2 确定性：是"重放确定"，不是"契约确定"

注入 offset 固定后，只要网络里**只有**这一个集合通信，分组交换的仲裁结果逐周期可复现——等待仍然存在（16×16 时 max_ramp_wait 高达 123 cycles，32×32 时 500），但等待时长是排图的确定输出，不是随机变量。问题在于封闭世界假设：一旦有背景流量共享缓冲和仲裁，确定性立即失效。①号 NC 数据中 PRIO_DYN（给集合流最高优先级的动态仲裁）在背景流下 coll_delay=1,800 cycles、需要 168 flit 缓冲——**优先级挡不住已经在缓冲里的类间耦合**。

### 3.3 代价：缓冲即面积，且随规模增长

- 16×16 达界配置的峰值缓冲 118 flit 集中在 ramp（链路缓冲仅 10）——64 B flit 下就是 7.4 KiB SRAM/热点。
- ②号面积模型里，axis+CCW 从零缓冲（面积 1.027×，t1=155）推到全下界（t1=96, II=47）需要 W=4/B=11，面积 **1.356×** 基线——**+32% 面积买 38% 时延**（155→96）。Pareto 前沿（`results/multiflit_area_makespan.png`）清楚显示这是一条凸的收益递减曲线。
- 参照系：满配输入队列 VC 路由器的缓冲（5 端口×2VC×20 深）= 200 flit = 12.5 KiB，占路由器面积模型的 36.5%。缓冲是路由器里最贵的东西。

**小结**：这条路线能达到"性能下界 + 封闭世界下的重放确定性"，达界所需缓冲不大（每输入 2~11 flit 量级），但确定性不构成对背景流量的契约，且把面积花在了本可以不花的地方。

## 4. 问题三：源端注入控制 + router calendar 排图，能达到多少？

这条路线更进一步：离线排图精确到**每条链路每个时隙**，路由器按全局时间查 calendar 表转发（slot → in_port, out_port_mask, opcode），集合通信 flit 零缓冲直通（cut-through），不做路由计算、不做 VA/SA 仲裁。图论视角：这是对时间展开图（time-expanded graph）做一次严格的边着色，排图可行 = 无冲突有证明。排队论视角：到达曲线与服务曲线逐槽相等，backlog 恒等于 0——不是"期望为 0"，是构造性为 0。

### 4.1 确定性：契约级，对背景流量免疫

①号 NC 数据里 CAL_SOFT 在背景注入率 λ 从 0.02 扫到 0.3 的全部工况下，六种集合通信的 coll_delay **全部精确等于排图 makespan、coll_buf 恒为 0**：broadcast 94、gather/allgather/allreduce 188、alltoall 384。这是 buffer 路线给不出的性质：时延不依赖网络里还有什么，只依赖排图本身。违规流量（迟到/早到/错端口）由 watchdog 检测后降级到 XY escape 路径，不丢包、不挂死。

### 4.2 性能：刚性税存在，但随规模消失

零缓冲的代价是排图失去"原地等 1 拍"的自由度，flit 一旦注入必须像刚体一样滑到底，排图变成刚性 footprint packing。实测的刚性税（③号，allgather，vs eject 界）：

| 规模 | 零缓冲最优（方案） | eject 界 | 比值 |
|---|---:|---:|---:|
| 4×4 | 32（hybrid_bi B=2） | 15 | 2.13× |
| 8×8 | 102（hybrid_v_bi B=2） | 63 | 1.62× |
| 16×16 | **334**（hybrid_v_bi B=2） | 255 | **1.31×** |
| 32×32 | 1,182（hybrid_v_bi B=2） | 1,023 | 1.16× |
| 64×64 | 4,412（hybrid_v_bi B=2，近零缓冲†） | 4,095 | 1.08× |

† 64×64 点的残余等待 ≤3 拍（`zerobuf_64x64_witness.json` 中未获严格零缓冲认证）；严格认证零缓冲的方案（ring_uni）makespan 为 24,322，实用上应按"每输入 1~3 flit 对齐缓冲"理解。若再放宽到 B=4 的少量缓冲，可到 4,164（下界 4,121 的 1.01×）。

两个要点：

1. **刚性税是小规模/时延绑定区间的现象**。规模一大，问题进入带宽绑定区，注入 offset 这一个自由度就足够把链路排满，比值趋近 1（32×32 为 1.16×，64×64 允许 1~3 拍对齐缓冲时 1.08×，B=4 时 1.01×）。broadcast/reduce 类树形集合在 8×6 上零缓冲即可达 110（LB=96，+15%），本来就没多少税可收。
2. **方案选择比缓冲更重要**。同在 16×16 零缓冲下，multitree 837 vs hybrid_v_bi 334——排图算法的好坏是 2.5× 的差距，远大于"有无缓冲"的差距。alltoall 的对照实验同样说明问题：刚性 pack 1,068（+15% vs 界 929），带一个二分槽缓冲即命中 929——**大多数刚性税可以用"极少量、位置正确的缓冲"或"更聪明的排图"赎回**。

### 4.3 代价：calendar 表便宜，贵的是全局时间

`results/impl_schemes.json` 给出三种实现同一批排图树的机制对比（8×6，每 router）：

| 机制 | 头开销 | router SRAM | 相对面积 | 需要全局时间同步？ |
|---|---:|---:|---:|---|
| 源路由（header 带转发码） | 8 bit | 72 bit | 0.00011 | 否 |
| **router calendar** | 0 | 1,472 bit | 0.00221 | **是** |
| 混合染色（2-color 静态路由） | 1 bit | 80 bit | 0.00012 | 否 |

calendar 的 SRAM 是源路由的 ~20 倍，但绝对量可忽略（占路由器面积 <1%；6×8 全集合日历 dense 3.25 KiB，利用稀疏性压到 5,888 bit，−78%）。真正的架构性代价是**全局时间基准**和排图的离线计算/下发通道。若集合通信的树结构不多（本例 48 棵树、每 router 最多 9 种配置），源路由或染色方案可以在不要全局时间的前提下逼近同样效果——这是一个常被忽略的降级选项。

**小结**：calendar 路线给出的是**无条件（契约级）确定性 + 零网内缓冲**，性能上小网络付 15–30% 刚性税、大网络免税；硬件增量本身接近免费。

## 5. 问题四：考虑面积，最佳方案长什么样？

把前两节放到面积轴上，结论会反直觉地干脆：**确定性不是花面积买来的，而是省面积省出来的**——因为确定性的对立面（无准入的动态排队）才是缓冲面积的根源。本仓库五轮架构迭代（②/①号设置，解析 PPA，相对基线 IQ-XY 路由器 = 1.00）：

| 迭代 | 关键动作 | 相对面积 |
|---|---|---:|
| Arch-A | dense calendar + 网内 combine | 1.065× |
| Arch-A2 | 去掉网内算术（reduce 改为 gather + PE 本地算） | 1.028× |
| Arch-A3 | calendar 稀疏化（−78% SRAM） | 1.000× |
| Arch-A4 | 背景流缓冲改共享池（100→50 flit） | 0.822× |
| **Arch-A5（最终）** | 多播复用 calendar 的 out_port_mask（CalFork），池缩到 38 flit | **0.746×** |

Arch-A5 面积分解：crossbar 0.380 + 背景流共享池缓冲 0.139 + 控制 0.193 + 稀疏 calendar 0.009 + CalFork 多播 0.025 = **0.746**。省出 25.4% 的来源一目了然：**集合通信路径上一个 flit 的缓冲都没有**（基线的 VC 缓冲项 0.365 → 0.139，只剩背景流量的份额）。

由此提炼确定性低时延集合通信的**面积最优设计法则**：

1. **确定性放在信息最全的地方。** 集合通信的全部结构编译期已知，就在编译期把冲突解干净（离线排图 + 源端注入 offset），运行时硬件只做重放。让路由器在运行时用缓冲/仲裁重新发现编译期就知道的答案，是双重浪费：先花面积存等待的 flit，再花时延等仲裁。
2. **零缓冲直通留给集合流，小共享池留给背景流，软优先缝合两者。** 硬 TDM（1/16 槽）会把背景流时延推到 44,336 cycles；软优先（calendar 事件命中时集合流赢，否则背景流用）把背景流 12-hop 进度上界压到 ~160–188 cycles，且不向集合流引入任何抖动。
3. **网内不做算术。** router combine 只为 allreduce 省 ~2× makespan（Tier B 101–228 vs Tier A 229–575 cycles），但把面积从 1.028× 推回 1.065×+，还引入 flit 级算术的验证负担。面积优先时选 gather + PE 本地归约 + broadcast（Tier A）。
4. **多播复用排图基础设施。** calendar 槽自带 out_port_mask，fork 是免费副产品（0.025 面积增量 vs 通用多播单元 0.058）——集合通信 91–95 cycles 的 broadcast 不需要任何额外回放周期。
5. **刚性税用"排图算法 + 极少量对齐缓冲"支付，不用深缓冲支付。** 16×16 的 334→281 这最后 19% 靠的应该是更好的 packer（或每输入 1–2 flit 的转角对齐），而不是 118 flit 的 ramp 缓冲。
6. **保底路径必须存在但不必快。** watchdog + 降级 XY escape 保证违规流量不丢不挂，确定性契约只对守约流量生效——这是确定性系统能与开放系统共存的前提。

一句话概括最佳方案：

> **源端注入控制（编译期排图产出 offset） + 稀疏 router calendar 零缓冲直通（集合流） + 小共享池分组交换（背景流） + 软优先隔离 + watchdog 降级**。它同时拿到：集合通信时延 = 排图 makespan（无条件确定，大规模下距下界 8–16%，配每输入几拍的对齐缓冲可压到 1%）、背景单播有界进度、以及比基线分组交换路由器**还小 25%** 的面积。

## 6. 尾注：三套语言各自贡献了什么

- **图论**给了不可逾越的地板（五族下界）和"该修哪里"的诊断——dilation 告诉你树选得好不好，congestion 告诉你 II 的极限，割告诉你瓶颈在 ramp 还是 bisection。
- **排队论**（含网络演算）解释了地板之上那 99% 从哪来（到达过程 × 服务纪律的失配），并证明了两条消除路径的本质区别：整形到达（buffer 路线，backlog 有界）vs 逐槽契约（calendar 路线，backlog 恒 0）。
- **系统观**负责算总账：确定性应该放在源端和编译期，缓冲是动态性的物化成本，省掉动态性就省掉了面积——最优解在"更少的硬件"而不是"更多的硬件"一侧。
