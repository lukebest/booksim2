# 8×6 无缓冲折叠 2D torus 上的集合通信：paper 机制基线 + 静态拍图方案

**几何：** 8×6，48 节点；6 行环×8 + 8 列环×6 = **192 条有向弧**（96 无向，与折叠 torus 链路集逐条相同，金属 96/82 = 1.17× mesh）。挂接方式推导完之后这就是一个**无缓冲折叠 2D torus**：每个节点既是行环站也是列环站，环内零缓冲、零转环驻留，两维各有双向车道，折叠布线让最长单线只有 2 个核间距
**链路时延口径（本轮更新，见第 2 节）：** 横向 1 个 core pitch = **5 拍**、纵向 = **7 拍**；折叠后环上相邻两核在版图上隔着一个核，所以**典型一跳 = 2 个 pitch**（行 **10** 拍 / 列 **14** 拍），每环另有两段落在折返处只跨 1 个 pitch（5 / 7 拍）；**换环过桥 t_turn = 10 拍**；RAMP = 2、RAMP_BW = 2
**挂接方式（已推导）：** 每个 AI core 花掉它的 **2 个环口 = 1 个行环口 + 1 个列环口**；两个维度都用**双向全环 + 折叠布线**；**桥与核同址、复用这两个口**，48 个桥的额外环上抽头为 0。这不是假设而是从「≤2 口 + 连通性 + 割容量 + 线长」四条结构约束里筛出来的，九个候选方案的对照见 `results/ring_attach_8x6.json` 与报告 §1
**判据：** 环用 **D-R 五子句**（R1 弧互斥 / R2 上环互斥 / R3 下环互斥 / R4 转环原子 / R5 VOQ 保序+静态定路），与 `islip2d-mesh-ring-8x6.md` 同一套
**基线（Part 1）：** `ring_base` = HPCA'22 机制（E-tag / I-tag + 偏转 + 桥 transfer FIFO + 目的端重组），**只支持 unicast**；`ring_islip2d` 作同能力对照
**静态拍图（Part 2）：** 环站支持 **copy-and-continue 弧多播**，归约在**节点 L1 buffer** 内做；环内仍严格零缓冲、零转环驻留
**能力分层：** T0 = 纯 unicast（paper 机制可达）；T1 = 弧多播 + L1 归约
**数据：** `results/ring_collectives_8x6.json`、`results/ring_tavg_8x6.json`、`results/ring_robust_8x6.json`、`results/ring_attach_8x6.json`、`results/ring_throughput_8x6.json`（路由无关下界 + 两条腿的 II/带宽利用率）、`results/ring_bridge_8x6.json`（**本轮新增：48 个桥 FIFO 的逐桥占用、深度扫描、t_turn 扫描**）、`results/calendars/ring_*.json`；mesh 参照 `results/multiflit_area_makespan.json`
**验证：** `results/verify_ring_collectives_8x6.json`，**107/107 通过**，全部可执行、失败即命名具体量；其中 **7 项记录为「预测被推翻」**而不是悄悄放宽
**报告：** `results/report_ring_collectives_8x6.html` —— 无缓冲环工作的**唯一**报告（中文）。§1 挂接方式推导、**§2 链路时延口径**、§3 路由无关下界、§6 makespan 主对比、**§10 各 bridge 的 buffer 占用**、§13 II 与带宽利用率、§14 T_avg、§15 容错、§16 抗抖动。mesh 侧的 R=1/5/13 深度扫描属于 mesh 既有工作，留在 `results/report_multi_area_makespan.html` §5.5

## 0. 一页结论

1. **本轮最大的口径变化：桥从记账细节变成了绑定资源。** 过桥 10 拍意味着一个转环 flit 要占住桥 FIFO 一个条目 10 拍；到达率不变、停留时间涨 10×，占用就涨 10×。同一段 flat alltoall 基线，旧口径（每跳 7/9 拍、过桥 1 拍、不折叠）下是 **164 拍**（m=1）/ **1928 拍**（m=13），新口径下是 **284 / 2831 拍**（1.73× / 1.47×）；因桥满被打偏的次数从 **40 涨到 485**（m=1）。**贵的不只是线，更是桥。**

2. **10 拍的桥直接改了算法排名。** m=1 广播上，`dim_2phase`（**76 拍**）现在快过 `flat`（**83 拍**）—— 前者路径更长但**一次桥都不过**，后者路径更短却要在关键路径上付 10 拍。旧口径下是 `flat` 赢。**换维贵到什么程度，决定了该按维分解还是该直接绕环。**

3. **过桥不再是最便宜的换维方式，这改了下界的定义。** 0→9（差一行一列）走桥是 10+14+10 = **34 拍**，落 L1 中继再上列环是 10+14+2 = **26 拍**。所以时延地板只能收 `min(t_turn, RAMP) = 2` 拍，否则按维分解的拍图（它根本不过桥）会「低于下界」—— 那不是它违规，是界算错了。

4. **48 个桥 FIFO 是基线唯一赖不掉的在途存储，而当前深度不够。** 默认 `fifo_depth=4`(+1 E-tag 保留位)下，m=13 的六个 pattern 里有 **5 个**峰值顶格；alltoall m=13 因满被打偏 **16668 次**、最忙桥 24.6% 的时间是满的。把深度从 1 扫到 32：alltoall m=1 **657 → 156 拍（4.21×）**、m=13 **7087 → 1648 拍（4.30×）**。**深度 1（「桥就是一级寄存器」）在 10 拍的桥下不是一个设计点**；m=1 在 16 条走平，m=13 到 32 条仍在降。

5. **桥 buffer 的需求很大程度上是 t_turn 造出来的，所以缩短过桥比加深 FIFO 划算。** 把 t_turn 从 1 扫到 10：alltoall m=13 平均桥深度 **×2.25**、因满打偏 **×3.07**、makespan **×1.50**；m=1 更敏感（makespan ×1.68、打偏 **×23.1**）。**这是这套设计里性价比最高的一个优化点。**

6. **fan-in 的桥负载不均匀，fan-out 均匀。** alltoall 用满 48 个桥、最忙/平均 = 1.06；gather 只用 **5 个**桥（root 那一列与那一行的交汇点），最忙/平均 = 1.25，热点固定在 root 的行列交点。**按 root 位置差异化配深度是有意义的，统一深度会在热点先满。**

7. **静态拍图对桥的要求不是「更小」而是「确定」。** `dim_2phase` 系列**一次桥都不过**（4/4 对照方案过桥次数为 0），桥 buffer 成本整个删掉；而 `flat` 系列过桥更狠 —— alltoall m=1 把 1680 次过桥压进 107 拍，需要**同时 17 个条目**停在同一座桥上（基线现在只有 5 个）。差别在于拍图那 17 个是编译期算死的常数、不需要仲裁也不会打偏，基线那 5 个是运行期赌出来的分布还要白吃 485 次绕圈。**桥面积给得起就上 `flat` 换 makespan，给不起就上 `dim_2phase` 走 L1 中继。**

8. **弧多播仍是唯一改变数量级的硬件增量，且只对 fan-out 生效。** m=13 broadcast 同一棵树：上环 flit **611 → 182**、传输数 **47 → 14**、makespan **179 → 108 拍**。但 `reduce`/`gather`/`alltoall` **没有 T1 行，这不是漏跑**：fan-in 无可复制，alltoall 的 N(N−1) 条消息两两不同。验证套件断言「多播不适用时 T1 与 T0 逐字段相同」（17 个 (pattern, algo) 对）。**买多播硬件对这三个 pattern 的收益精确为 0。**
   而且这是**带宽**收益不是**时延**收益：m=1 时同一对 T1/T0 都是 **76 拍**，一拍不差。

9. **T0 下必须承认两条恒等式，否则整张表在自我恭维。** `allgather` 与 `alltoall` 是**同一个 unicast 流集**（实测 flat/T0 逐项相同：m=1 均 107 拍 / 基线 284 拍，m=13 均 1097 / 2831）；`gather` 与 `reduce` 是**同一个网络需求**，差别只在 root 的 L1 是否累加。真正的差异必须落在 **T1 能力**与**归约点的 L1/ramp 瓶颈**上。

10. **m=1 时六个集合通信的最优拍图全部精确压在时延地板上。** 结构地板一律 **72 拍**纯线延迟（直径，含按 ramp 收的换维），容量项最大只有 48 拍。**「加宽布线 / 加多车道」对单 flit 集合通信毫无用处**，该动的是跨度与相位数。m=13 才切换：`gather`/`allgather` 撞核端口 = L1 ramp 的 **306 拍**，`alltoall` 撞 cut 的 **624 拍**。

11. **paper 机制在漏斗型集合通信上仍然打赢静态拍图。** m=13 `reduce`：`ring_base` **110 拍** vs 拍图 **178 拍**（拍图慢 1.62×）。机理不是偏转有魔法，而是**下环端口的记账粒度**：拍图把一个抽取点整段（m·σ 拍）独占给一次传输，`ring_base` 按 L1 的 `RAMP_BW` 逐 flit 交错抽取。放宽到 2 个环口后 reduce **178 → 126 拍**（1.41×）、gather/dim **659 → 425**（1.55×）、allgather/T1 **849 → 498**（1.71×）。**这一列必须公开，否则「静态拍图全面更快」是错的。**

12. **反过来，在扇出与全交换型上拍图大幅领先，且新口径下差距拉大了。** m=1 `alltoall`：拍图 **107** vs base **284**（**2.17×**）；m=13 **1097** vs **2831**（2.58×）。m=13 `broadcast` 拍图 **108** vs base **219**（2.03×）。原因正是第 1 条：基线要过桥，而过桥现在很贵。

13. **`ring_base` 曾看起来跑到「理论下界」以下（最狠 0.73×），那是记账错不是物理。** 40 行里 **18 行**受影响。根因是把**拍图模型**的界拿去除**另一台机器**上的实测。本轮之后两台机器的差别**只剩两处**（环站出口 1 flit/拍 vs 按 `RAMP_BW` 排空、拍图每相位多收 +RAMP）—— **过桥这第三处已经统一：两边现在都收 t_turn=10**。在基线自己模型下重建界后 **40 行全部 ≥ 下界**。

14. **`II_eff` 可以掉到容量界以下，它不是可以拿去校验下界的量。** `gather/flat` 在 R=5 时 `II_eff=11.8` 拍而容量界是 24 拍（**0.49×**），R=13 收窄到 0.82×。改用均摊值 `T_R/R` 之后恒 ≥ 界。**违反下界的不是机器，是那个指标的定义。**

15. **连着做的时候「带宽利用率」必须拆成占用与有用两个。** 流水稳态（R=13 均摊）`alltoall` 基线 **1975.2** vs 拍图 **963.4** 拍/轮（**2.05×**，II 界 624）；但 `gather` 上两条腿都贴着 L1 ramp 界，谁也赢不了。关键在利用率：`gather/flat` m=13 基线**占用** 26.8%、**有用**只有 2.6%，差出来的 **10.3×** 全烧在绕着 root 转圈上，拍图 hop tax 恒为 **1.00**。**把「弧上有东西在跑」当带宽利用率，会把浪费读成产出。**

16. **「环比 mesh 快」在新口径下不再成立，而且这张表现在是跨口径的、不能直接读。** mesh 一侧仍是旧线延迟（H=7/V=9、过桥 1 拍），环一侧已换成新口径。在这个跨口径对照下：**1 端口的环三档全输**（1.115× / 1.213× / 1.428×），**2 端口的环** R=1/5 赢（0.969× / 0.975×）、R=13 打平（1.002×）。要做真对比必须先把 mesh 也搬到同一套 pitch 上重跑，本轮未做。

17. **打到下界与抗故障 / 抗抖动是互斥的。** `allgather/ring_rotate` 的 II_eff **= 47.0 = 弧负载下界**（全场最优），代价是 27 个故障场景里 **20 个无解**、J=256 burst 下吸收 **0 拍**；同 pattern 的 `dim_2phase/T1` 只有 1 个不可行。**这两件事是同一个性质。**

18. **一个死节点会逼出一个额外相位，而不只是重排一次。** 维度切片靠**行列唯一交点**转交数据；交点死了，整列都拿不到那一行 —— fabric 仍连通，但拍图只有一条路。`allgather/dim_2phase/T1` 的 26 次重编译里 **12 次**必须追加修复相位。把这些报成「重编译，膨胀 1.2×」会掩盖一个缺失的相位。

19. **挂接方式不用挑，四条结构约束就把它筛成唯一解；而「half ring 更省」是错的。** 拆环**不改变段数**（96 条无向段，九个方案完全一样），省的只是线长（2.0× → 1.85× mesh）；而**错位**半环反而更费金属（**2.15×**）且需要一根跨 6 个核间距的长线。半跨环在「≤2 口」下直接不连通（可达对只有 1104/2256），补缝就得把 x 向对分从 12 砍到 6 flit/cy。

## 1. 口径：什么叫一次「被授权的传输」，多播怎么记账

沿用 `rg-noc-8x6.md` 的左闭右开区间语义。unicast 印记 `RingFootprint` 由 `(src, dst, ring, direction, t0, m, σ)` 完全决定。

多播新增 `RingMcastFootprint`：**一次 board、弧上多个 leave、可选 `op=ADD`**：

- **R2（上环互斥）**：一次多播只占**一个**上环点，这正是它省下来的东西。
- **R3（下环互斥）**：弧上**每个成员各占一个抽取点**——多播不能省下环带宽。
- **R4（转环原子）**：**每个转环副本各查一次**，且现在各自占住桥 `t_turn` 拍。
- **R1（弧互斥）**：覆盖弧的每条段各占一次，与 unicast 同。

## 2. 链路时延口径：折叠布线与 10 拍的桥

所有 makespan、所有下界都是这组数乘出来的。口径只有三个输入量，其余全是推出来的。

| 口径项 | 值 | 来源 / 算法 |
|---|---|---|
| 横向物理相邻两核（1 pitch） | **5 拍** | 输入口径 |
| 纵向物理相邻两核（1 pitch） | **7 拍** | 输入口径 |
| 换环过桥 `t_turn` | **10 拍** | 输入口径；flit 在桥 transfer FIFO 里被搬到另一个环 |
| 行环典型一跳（折叠后隔 1 个核，2 pitch） | **10 拍** | = 2×5，每行环 6 段 |
| 列环典型一跳（2 pitch） | **14 拍** | = 2×7，每列环 4 段 |
| 行 / 列环折返端一跳（1 pitch） | 5 / 7 拍 | 每环各 2 段 |
| 落 L1 再上另一个环（RAMP） | **2 拍** | 换维的**另一条**路，比过桥便宜 5× |
| 行环一圈线延迟 | **70 拍** | 6×10 + 2×5 |
| 列环一圈线延迟 | **70 拍** | 4×14 + 2×7，与行环同长 |
| 最远两核零竞争时延（直径） | **72 拍** | 7 跳，换维按 ramp 收 |
| 全部 2256 个有序核对的平均时延 | **43.19 拍** | 平均 3.57 跳 |

折叠的要点是「环上相邻 ≠ 物理相邻」：环上编号 0→1 的两个核物理上中间还隔着一个核。一圈总线长两种画法都是 2(k−1) 个 pitch，**折叠不省金属，只把最长的那根摊平**（展开画法有一根 35 拍的绕回长线，折叠后没有任何一根超过 10 拍）。

三个后果，每一个都改了结论：

1. **跳数不再等价于拍数。** 一跳可能 10 拍也可能 5 拍。好消息是**最短跳数路径仍然就是最短时延路径**：两段折返端在环上正好隔半圈，任何半圈弧都恰好含其中一段，两个方向的账仍然对得上（2256 对全测）。
2. **过桥不再是最便宜的换维方式**（第 0 节第 3 条）。所以时延地板只能收 `min(t_turn, RAMP)`。实现上：环上每一段单独收自己的拍数（`link_lat`），不再用「每环一个平均跳延迟」；地板在 `(core, 所在环)` 状态图上跑 Dijkstra。
3. **桥成了绑定资源**，单独占第 6 节。

**旧口径未被静默改掉：** `ring_islip2d` 那条集中式参照线与第 5 节的 mesh 参照仍是旧的 H=7/V=9、`t_turn=1` 口径（`LEGACY_WIRE` 显式钉住），所以那两处的绝对拍数**不能**与本节口径下的数直接相减。

## 3. 六个集合通信的路由无关下界

这一节的界**只依赖拓扑与端口**，不依赖 transport、不依赖能力分层（T0/T1 同界）。刻意取**最弱**的一版：允许任意中继、允许沿途本地合并、换维按 `min(t_turn, RAMP)` 收，所以「谁都不能低于它」成立，而「贴着它就最优」不成立。

四条界：**cut**（x=1 / y=1 两条直割，容量 12 / 16 flit/cy）、**core port**（一个核 2 个环口）、**L1 ramp**（RAMP_BW=2 flit/cy）、**latency**（零竞争最短路时延 + 消息串行化尾巴）。前三条是**容量界**（=II 界）；makespan 的界是 `max(容量界, 时延地板)`。本机器上 `2 个环口 = RAMP_BW`，所以 port 与 ramp 两条界数值恒等。

| collective | m | cut | port = ramp | 容量界（=II 界） | 时延地板 | makespan 界 | 绑定 |
|---|---|---|---|---|---|---|---|
| broadcast | 1 | 1 | 1 | 1 | 72 | **72** | latency |
| reduce | 1 | 1 | 1 | 1 | 72 | **72** | latency |
| allreduce | 1 | 1 | 1 | 1 | 72 | **72** | latency |
| gather | 1 | 2 | **24** | 24 | 72 | **72** | latency |
| allgather | 1 | 4 | **24** | 24 | 72 | **72** | latency |
| alltoall | 1 | **48** | 24 | 48 | 72 | **72** | latency |
| broadcast | 13 | 2 | 7 | 7 | 84 | **84** | latency |
| reduce | 13 | 2 | 7 | 7 | 84 | **84** | latency |
| allreduce | 13 | 2 | 7 | 7 | 84 | **84** | latency |
| gather | 13 | 26 | **306** | 306 | 84 | **306** | port |
| allgather | 13 | 46 | **306** | 306 | 84 | **306** | port |
| alltoall | 13 | **624** | 306 | 624 | 84 | **624** | cut |

三条结论：

1. **m=1 时六个集合通信全部是距离问题，不是带宽问题**（第 0 节第 10 条）。
2. **m=13 才有三个模式换成容量界**：fan-in 的 306 拍是「root 的 L1 每拍只吃 2 个 flit、要吃 47×13 = 611 个」，这是**外设界**而不是网络界，加环带宽一分钱都省不下来。
3. **broadcast / reduce / allreduce 的容量界弱到个位数（7 拍）**，那几行的「比下界」倍数衡量的是相位链而不是资源。

实测离界多远（m=1 最优拍图 / 结构地板）：broadcast **1.06×**、reduce 1.06×、gather 1.15×、allgather 1.49×、alltoall 1.49×、allreduce **2.11×**（最松的是 allreduce，它要串起最多相位，而地板只按最远那条直线算）。

## 4. Part 1：paper 机制的六个集合通信

三条腿跑同一个流集、同一 m、同一 σ、同一 barrier 语义。两列都取**各自腿的最优算法**（集合算法与 transport 是正交轴，拿同一个算法压基线会把基线做成稻草人），所以同一行的两个数字可能来自不同算法。

**「下界」一列是拍图机器模型下的界，不能拿去除 `ring_base`。** 两条腿的机器差别现在只剩两处（第 0 节第 13 条）。`base/其自身模型下界`一列才是量基线的正确口径。

**m = 1**（六个最优拍图全部精确等于时延地板）

## 5. Part 1b：allgather 的 T_avg（R = 1 / 5 / 13）

定义与 mesh 侧一致：自由多轮 rigid pack 实测 `T_R`，`II_eff = (T_R − T1)/(R − 1)`，`T_avg = (T1 + T_R)/2`。

| 方案 | ports | T1 | T₅ | T₁₃ | II_eff | T_avg(1) | T_avg(5) | T_avg(13) |
|---|---|---|---|---|---|---|---|---|
| flat / T0 | 2 | **93** | 290 | 680 | 48.92 | **93** | 191.5 | 386.5 |
| dim_2phase / T1 | 2 | 112 | 240 | 527 | 34.58 | 112 | **176.0** | **319.5** |
| flat / T0 | 1 | **107** | 331 | 804 | 58.08 | **107** | 219.0 | 455.5 |
| dim_2phase / T1 | 1 | 128 | 348 | 800 | 56.00 | 128 | 238.0 | 464.0 |
| dim_2phase / T0 | 1 | 134 | 420 | 1016 | 73.50 | 134 | 277.0 | 575.0 |
| halving_doubling / T0 | 1 | 287 | 1064 | 2592 | 192.08 | 287 | 675.5 | 1439.5 |
| ring_rotate / T0 | 1 | 799 | 987 | 1363 | **47.00** | 799 | 893.0 | 1081.0 |

**环内部排序会随 R 翻转，这是新口径带来的变化**：R=1 时 `flat` 最优（时延地板拼的是最短临界路径），R=5 起 `dim_2phase/T1` 反超（II_eff 更小）。旋转虽然 `II_eff` 最小（47.0 = 弧负载下界，全场最优），但 T1=799 的填充代价要摊到 R≈149 才可能翻盘 —— **II_eff 最优 ≠ T_avg 最优**。

### 环 vs 8×6 mesh（**跨口径，不能直接读**）

mesh 侧扫自己的设计变量（crossbar 写宽度 W、抽取率 E、FIFO 深度 B，378 个设计点）。**这张表里 mesh 一侧仍是旧线延迟（H=7/V=9、过桥 1 拍），环一侧是第 2 节的新口径**，所以比值只能读成「各自口径下两者的流水行为形状」，不能读成「环打不打得过 mesh」。

| R | mesh 最优 | mesh T_avg | 环 T_avg（1 端口） | ring/mesh | 环 T_avg（2 端口） | ring/mesh |
|---|---|---|---|---|---|---|
| 1 | axis+CCW | 96 | 107 | 1.115× | **93** | **0.969×** |
| 5 | axis+CCW | 180.5 | 219.0 | 1.213× | **176.0** | **0.975×** |
| 13 | Hamilton bi-tree | 319.0 | 455.5 | **1.428×** | 319.5 | 1.002× |

两条仍然成立的结构性观察：**mesh 自己的最优方案在 R=13 换人**（axis+CCW → Hamilton bi-tree，深流水下 II_eff 支配一切）；**1 端口的环 R 越大输得越多**，因为绑定资源从跨度换成了环站那唯一一个上/下环点。

## 6. 各 bridge 的 buffer 占用（本轮新增）

环上没有缓冲，**桥上有**。要换环的 flit 必须在该节点的 transfer FIFO 里待着，光是过桥就占住一个条目 **10 拍**。48 个核每个都是桥，所以这是 48 个 FIFO，是环上唯一的在途存储。默认 `fifo_depth=4`（+1 个 E-tag 保留位）。

**满了不会阻塞。** 「已在环上的 flit 永不停」是硬不变量，桥满时到达的 flit 不是等，而是**被打偏绕一整圈再来**。深度不够的代价不是死锁，而是 makespan。

### 6.1 逐桥实测（`ring_base`，默认深度）

| collective | m | makespan | 最深条目 | 平均深度（最忙桥） | 满的时间占比 | 因满被打偏 | 用到的桥 |
|---|---|---|---|---|---|---|---|
| broadcast | 1 | 120 | 2 | 0.42 | 0.0% | 0 | 7 |
| broadcast | 13 | 828 | 4 | 0.79 | 11.0% | 306 | 7 |
| reduce / gather | 1 | 81 | 2 | 0.86 | 0.0% | 0 | 5 |
| reduce / gather | 13 | 551 | **5**(顶格) | 2.50 | 47.0% | 1142 | 5 |
| allreduce | 1 | 201 | 2 | 0.35 | 0.0% | 0 | 12 |
| allreduce | 13 | 1379 | **5** | 1.00 | 18.8% | 1448 | 12 |
| allgather / alltoall | 1 | 284 | 4 | 1.32 | 14.1% | 485 | 48 |
| allgather / alltoall | 13 | 2831 | **5** | 1.85 | 24.6% | **16668** | 48 |

**最深条目**是这座桥必须做多深，**平均深度**是它平时真正用到多少 —— 两者差得越远，说明这份深度是为瞬时突发买的。m=13 的五行顶到 4+1 的天花板，**顶格意味着深度是被参数卡住的，不是需求只有这么多**。

### 6.2 深度值多少钱（alltoall m=13）

| fifo_depth | makespan | 实际最深 | 最忙桥满的占比 | 因满被打偏 |
|---|---|---|---|---|
| 1 | 7087 | 2 | 56.3% | 57141 |
| 2 | 4357 | 3 | 41.5% | 33497 |
| 4 | **2831** | 5 | 24.6% | 16668 |
| 8 | 2023 | 9 | 20.1% | 7524 |
| 16 | 1872 | 17 | 15.9% | 2858 |
| 32 | 1648 | 33 | 16.9% | 971 |

「实际最深」一路跟着 `fifo_depth` 顶格，说明这条流量的**需求超过 32 个条目**；但 makespan 的收益递减。**建议值：至少 16 条**（m=1 在此完全走平、偏转归零），m=13 到 32 仍单调有收益。

### 6.3 是谁把 FIFO 填满的（t_turn 扫描）

占用 = 到达率 × 停留时间，而停留时间就是 `t_turn`。把桥从 1 拍加到 10 拍：

| 指标（alltoall） | m=1 | m=13 |
|---|---|---|
| makespan | ×1.68 | ×1.50 |
| 最忙桥平均占用 | ×2.91 | ×2.25 |
| 因满被打偏 | **×23.1** | ×3.07 |

**桥 buffer 的需求很大程度上是这次时延口径更新造出来的，不是流量本来就这么重。**

### 6.4 拍图这边的桥

拍图不排队：什么时候上桥、下桥编译期就定死了，没有「等一等」这个状态。所以这里统计的不是队列，而是**同一时刻停在同一座桥上的条目数**。

| 拍图 | m | 过桥次数 | 同时在桥上（峰值） | 对硬件的要求 |
|---|---|---|---|---|
| alltoall / allgather · flat | 1 | 1680 | **17** | 须能同时停 17 个，但不需要仲裁 |
| alltoall / allgather · flat | 13 | 1680 | 4 | 同上，4 个 |
| allreduce · flat | 1 / 13 | 70 | 5 / 2 | |
| broadcast · flat | 1 / 13 | 35 | 5 / 2 | |
| gather / reduce · flat | 1 / 13 | 35 | 3 / 2 | |
| **alltoall / allgather · dim_2phase** | 1 / 13 | **0** | **0** | **桥可以不存在** |

**`dim_2phase` 一次桥都不过**（4/4 对照方案），把桥 buffer 这项成本整个删掉，代价是中继核要有 L1 带宽接住它 —— 这正是第 2 节「过桥 10 拍比 ramp 2 拍贵」直接推出来的结论。反过来 `flat` 更依赖桥，但要的是**深度**而不是排队（第 0 节第 7 条）。

## 7. 吞吐（II）与带宽利用率：两条腿同一条公式

均摊值取 `per_round = T_R / R`（R=13），**不是** `II_eff`。利用率同时报两个数：**占用** = 弧上有东西在跑的比例，**有用** = 每个 flit 只按最短跳数记账；两者之比就是 **hop tax**。

| collective | m | II 下界 | 基线 拍/轮 | 拍图 拍/轮 | base/cal | 基线 占用 / 有用 | 基线 hop tax |
|---|---|---|---|---|---|---|---|
| gather | 1 | 24 | 29.3 | **24.5** | 1.19× | 11.2% / 2.1% | **5.45×** |
| gather | 13 | 306 | 365.3 | **314.3** | 1.16× | 26.8% / 2.6% | **10.32×** |
| alltoall | 1 | 48 | 146.5 | **61.9** | **2.37×** | — | — |
| alltoall | 13 | 624 | 1975.2 | **963.4** | **2.05×** | — | — |
| allgather | 1 | 24 | 81.5 | **61.5**（T1） | 1.32× | — | — |
| allgather | 13 | 306 | 661.6 | 668.9 | 0.99× | — | — |
| allreduce | 13 | 7 | **165.2** | 193.4 | 0.85× | — | — |
| broadcast | 13 | 7 | **141.2** | 142.5（T0）/ **56.2**（T1） | 0.99× | — | — |

四条必须一起读：

1. **fan-in 上两条腿都贴着 L1 ramp 界，谁也赢不了。** 要提速只能加 root 的 ramp 宽度。
2. **但基线是用 5~10 倍的带宽换来这个同样的吞吐的**（第 0 节第 15 条）。
3. **带宽受限的模式上拍图赢，而且新口径下赢得更多**：`alltoall` m=13 均摊 **2.05×**（旧口径 1.50×），m=1 **2.37×**（旧 1.42×）—— 差额几乎全部来自基线要过桥。
4. **深流水下排名会换人**：`allgather` m=13 均摊两条腿打平（0.99×）；`allreduce`/`broadcast` 均摊基线还略快，因为这两个的容量界弱到个位数，绑定的是相位链而不是资源。**T1 的多播在这里才是真增量：broadcast 均摊 142.5 → 56.2 拍/轮（2.53×）。**

## 9. 容错

场景集 = **27 个**：环特有的**绕回段失效**（5）+ 同环**分散死点**（4）+ 仓库既有的 link / node / quadrant 洞（18）。

| 方案 | 免重编译 | 可重编译 | 不可行 | 需修复相位 | 最坏做功归一化膨胀 |
|---|---|---|---|---|---|
| broadcast / dim_2phase / T1 | 9 | 17 | 1 | 2 | 1.42× |
| broadcast / flat / T0 | 6 | 20 | 1 | 0 | 1.01× |
| allgather / dim_2phase / T1 | 0 | 26 | 1 | **12** | 1.68× |
| allgather / flat / T0 | 0 | 26 | 1 | 0 | 1.10× |
| **allgather / ring_rotate / T0** | 7 | **0** | **20** | 0 | — |
| reduce / dim_2phase / T0 | 6 | 18 | 3 | 0 | 1.24× |
| reduce / flat / T0 | 5 | 21 | 1 | 0 | 1.01× |
| allreduce / dim_2phase / T1 | 6 | 20 | 1 | 2 | 1.26× |

修复相位是显式构造的：行/列相位交替，**持有缺失数据且与需要它的节点同环**的那个节点补发；每个缺失项**只指派一个供给者**——对归约型集合通信这一点是必须的，两个供给者会重复累加。

**膨胀比必须做功归一化**：死节点同时删掉容量**和工作量**，原始比会低于 1.0（那是阵列变小，不是丢节点让集合通信变快）。

## 10. 抗抖动

三种模型（`uniform_jitter` / `distance_skew` / `burst`）× J ∈ {0,2,…,512}，三种再同步策略：`global_shift`（硬 barrier，吸收恒为 0）、`phase_shift`（从不劣于前者）、`repack`（唯一能吸收的策略，重编译结果仍逐条通过 D-R 复核）。

| 方案 | makespan | J=256 burst 下吸收 |
|---|---|---|
| allgather / flat / T0 | 1097 | **203** |
| reduce / flat / T0 | 342 | 118 |
| allgather / dim_2phase / T1 | 849 | 71 |
| allreduce / dim_2phase / T1 | 286 | 39 |
| broadcast / dim_2phase / T1 | 108 | **0** |
| allgather / ring_rotate / T0 | 1363 | **0** |

抖动注入后**交付集合恒等**（48 个节点收到的 item 集合逐项不变），这是断言而不是计数比较。**松弛多的方案抗抖动，紧到界的方案不抗抖动**——这与第 9 节的旋转是同一个 trade-off 的另一面。

## 11. 与预期相反的结果（单列）

1. **10 拍的桥翻转了 m=1 的算法排名**（`flat` → `dim_2phase`）。原以为时延地板下「路径最短者赢」，实际是「过桥次数最少者赢」。
2. **L1 累加链那条杠杆的判定从「流量最少的不是最快的」变成了「就是最快的」**：旧口径下 halving_doubling 用 4.7× 流量换并发度仍能赢过 dim_2phase/T0，新口径下它的跨维跳每次多付 10 拍，反而最慢。**同一个杠杆在不同线延迟口径下判定相反。**
3. **旋转拍图链路利用率不到 1.0**（预测 1.0）。打到弧负载下界这半条成立，利用率那半条不成立。
4. **连续死点洞不需要环站 bypass mux**（预测「一个死点等于两处断环」）。2-连通环可以绕远路；mux 的价值在**分散死点**上。
5. **一个死节点逼出一个额外相位，而不是一次重路由**（第 0 节第 18 条）。
6. **双向半弧不减负载**（预测峰值弧负载减半）。多播弧无论朝哪边走都在同样站点丢副本，省的是 span。
7. **paper 机制在漏斗型集合通信上打赢静态拍图**（reduce m=13：110 vs 178 拍）。原因是下环端口的记账粒度而非偏转。
8. **T1 硬件对 alltoall / gather / reduce 的收益精确为 0**，且对所有 pattern 在 m=1 上的收益也精确为 0。
9. **`ring_base` 一度看起来跑到「理论下界」以下（最狠 0.73×）**，那是记账错（第 0 节第 13 条）。**能溜过去的原因是验证套件只断言了拍图 ≥ 界，从未断言基线 ≥ 任何界。**
10. **「half ring 省金属」是错的**：拆环不改变段数，只改变线长；错位半环反而更费（2.15× vs 2.0×）。
11. **基线那些「带宽利用率更高」的格子是浪费被读成了产出**（hop tax 最高 10.32×）。
12. **`II_eff` 可以掉到容量界以下**（最深 0.49×），它不是可以拿去校验下界的量。
13. **静态拍图不一定「更省桥」。** 原以为编译期确定性意味着更小的缓冲，实际 `flat` 在 m=1 上要 17 个条目，比基线的 5 个还深 —— 它换来的是**不需要仲裁、不会打偏**，不是更小。

## 12. 已知局限

1. **拍图与 `ring_base` 不共享一套机器模型（两处，已逐项量化）。** 环站出口 1 flit/拍 vs 节点按 `RAMP_BW=2` 排空；拍图每相位多收 `+RAMP=2`。（过桥这第三处本轮已统一。）要让头对头 makespan 也严格同硬件，得统一 `leave_ports` 与 `eject_bw` 后重跑全部拍图，本轮未做。
2. **mesh 参照仍停留在旧线延迟口径**（H=7/V=9、`t_turn=1`），`ring_islip2d` 同。所以第 5 节那张环 vs mesh 表是**跨口径**的，只能各自内部比。要做真对比必须把 mesh 侧也搬到 pitch 模型上重跑。
3. **桥 buffer 只量了占用，没有量面积/时序。** 「17 个条目的确定性缓冲」和「5 个条目 + 仲裁 + 打偏兜底」哪个更省面积，需要 RTL 级估算，本轮只给出条目数与是否需要仲裁这两个代理量。
4. **`t_turn=10` 是单一取值下的结论，只在 alltoall 上扫了 {1,2,5,10,20}。** 其余 pattern 的 t_turn 敏感性未测。
5. **归约建模为 item-set 并集 + 尺寸守恒折叠**，流量与依赖序精确，但**不含算术**：L1 内加法器的时延折进 `RAMP`。
6. **`ring_islip2d` 是 control 不是竞争者。**
7. **抖动只注入在源端释放时刻。** 飞行中抖动需要 transport 模型。
8. **故障重编译假设离线编译器拿到完整故障表。**
9. **σ = 1 贯穿全部拍图工作。** 金属恒定口径（环 σ=2）没有在本轮重跑。
10. **基线的 II 与利用率是「假设重排序缓冲无限大」下的读数。** 仿真器只统计溢出、不丢包、不反压，所以第 7 节里基线那几列偏乐观。
11. **第 3 节的结构界是刻意取弱的一版。** broadcast/reduce/allreduce 的容量界弱到 7 拍，那几行的「比下界」倍数不能当排图质量读。
12. **半环 fabric 上「排得好能追回多少」没有量。** 四道门槛与 12 个下界足以把候选排序，但要量就得让流集构造器和拍图编译器都支持非均匀环，本轮未做。
